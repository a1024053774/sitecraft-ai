# 契约命名统一 · 执行提示词（DeepSeek 用）
---

## 角色与总目标

你是我的项目的契约治理工程师。任务：统一数据契约的字段命名，消除同一概念在不同层的多名混用（已知实例：AI 操作叫 `update_card`/`add_card`，草稿模型里对应数组叫 `items`，模板层又出现 `slot`/`block`），最终让"模板 manifest → AI prompt → 操作校验 → 草稿 schema"四处的名字和容量约束来自同一个定义源。

## 项目背景（先读再动）

- Next.js 16 + React 19 + TypeScript，严格模式；无 ESLint/Prettier。
- 核心目录：`lib/`（123 个文件，含 zod schema 与生成逻辑）、`app/api/`（路由）、`components/`。
- 关键文件：`lib/site-document.ts`（zod schema，应成为单一真相源）、`lib/site-operations.ts`（AI 操作契约与校验）、`lib/template-composer.ts`、`lib/site-generator.ts`、`lib/site-intent.ts`。
- 已知病灶参考：prompt 手写文本与 schema 脱节曾导致 `features item 4 does not exist` 线上越界 bug（见 `docs/plans/2026-09-10-cleanup-and-product-contract.md`）。
- 存量状态：工作区可能有大量未提交改动。**开工前第一件事是 `git status` 并向汇报现状；若有未提交改动，先把它们按主题分组提交干净，作为基线。**

## 执行流程（五阶段，逐阶段等待放行）

### 阶段 1 · 冲突普查（只读，禁止改任何文件）

全量扫描所有契约定义点：zod schema、发给 AI 的 prompt 拼接文本、模板 manifest、校验逻辑、持久化数据结构。输出《冲突清单》表格，列固定为：

| 概念 | 各处名称 | 出现位置（文件:行号） | 语义是否一致 | 建议统一为 |

要求：每个"各处名称"必须给出至少一个真实文件:行号证据；语义可疑不同的（如 slot 可能专指"模板空位"而非"内容条目"）单独标注，不许强行合并。产出后停止，等我确认术语表。

### 阶段 2 · 术语表与单一真相源

1. 按我确认后的术语表写 `docs/glossary.md`：一词一概念，附反面清单（禁用同义词）。
2. 重构 prompt 生成路径：所有发给 AI 的字段名、路径、容量约束必须由遍历 `site-document.ts` schema 的函数生成；删除一切手写的平行契约文本。若现有代码结构做不到无损收口，提出最小改造方案并说明取舍，等我拍板。
3. 新增契约回归测试：断言生成的 prompt 中出现的每个 JSON path 都能在 zod schema 中 resolve；断言校验逻辑读取的是 schema 派生的容量声明，而不是按 op 名硬编码的 if。

### 阶段 3 · 分组改名

按术语表执行重命名。规则：
- 按模块分组，每组一个 commit，commit message 注明对应的 glossary 条目。
- **行为零变更**：只改标识符和字符串字面量中的字段名，不改任何函数逻辑、控制流、错误处理；不做顺手重构、不调整格式。
- 每组完成后依次跑 `npm run typecheck`、`npm test`，全绿才允许提交该组；任一失败立即回滚该组并报告原因。

### 阶段 4 · 存量数据兼容

凡涉及已落盘的草稿数据（`.sitecraft-data/` 或 Postgres）的字段改名：
- 禁止直接改读取端期望的字段名了事。必须引入 `schemaVersion`，读取时对旧字段名做前向 rename，保留至少一个大版本的 deprecation 窗口。
- 单独产出《迁移方案》（含回滚步骤），等我批准后才实施。

### 阶段 5 · 收口验证与交接报告

1. 抽查验证：任选 3 个字段（必须含 features 数组元素），从模板 manifest、AI prompt 生成结果、操作校验、草稿 schema 四处各贴一段真实代码/输出，证明同源。
2. 跑一次 `npx playwright test`（e2e 存在且你之前改动过主流程相关代码时必跑；若环境跑不动，明确说明并跳过，不要谎报）。
3. 写 `docs/plans/<日期>-contract-unification-report.md`：改了哪些组、每组 diff 统计、测试结果原文摘录、未尽事项。这份文档是你交付的一部分，没有它视为未完成。

## 硬性红线（违反任何一条 = 本阶段作废回滚）

1. 未获阶段放行不得进入下一阶段；阶段内连续动作不得超过上述定义范围。
2. 禁止 `git push --force`、禁止改写已有 commit、禁止删除任何非本次自产的文件。
3. 禁止修改 `.env*` 文件内容；禁止连接生产数据库。
4. 遇到术语表未覆盖的新概念冲突、或发现某处"看起来该改但改了会变行为"的情况：**停止并提问**，不许自行发明名字或猜测意图。
5. 禁止在报告中出现未经实际运行验证的"已通过/已完成"表述；测试输出必须原样粘贴。
6. 单个新文件超过 300 行或单组 diff 超过 800 行时，先停下来拆分方案再动手。

## 验收标准（我方将独立复核，请照此自检）

- 《冲突清单》中每一行都能在我项目当前代码中定位到证据。
- 全局搜索被禁用的同义词（如统一后搜 `\bslot\b`、`\bblock\b` 等，按最终术语表），除白名单历史文档外零命中。
- 生成的 AI prompt 全文中不存在任何手写字段名字符串（grep 验证）。
- typecheck、单元测试全绿；报告中的测试输出与我本地复跑一致。
- 随机挑一个板块的容量数字，四处来源指向同一个常量/schema 节点。
