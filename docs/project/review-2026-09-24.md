### 需要修的缺陷

**A1 内置浏览器拦截沙箱 iframe（第 1 项根因）**

- 证据：同一页面内逐个插入 iframe，结果如下。同一个预览 URL，去掉 `sandbox` 后返回 200；连 `/api/health` 加上 `sandbox` 也被拦。

  | sandbox 属性 | 结果 |
  | --- | --- |
  | 无 | 200 |
  | `allow-scripts allow-forms allow-same-origin` | 200 |
  | `allow-scripts allow-forms`（当前值） | ERR_BLOCKED_BY_CLIENT |
  | `allow-scripts` / 空字符串 | ERR_BLOCKED_BY_CLIENT |

- 影响：负责人在这类浏览器里打开工作台、发布页、/quality，所有预览都失败；在普通 Chrome 里正常，所以 Codex 和 Cursor 都没复现到。
- 可选方案（需负责人二选一）：
  1. **不改代码**：盲评和日常查看改用 Chrome/Safari，失败提示里直接写明“当前浏览器拦截了沙箱预览，请用 Chrome 打开”。成本最低。
  2. **预览走独立源**：预览 iframe 改用另一个源（开发环境可用 `localhost:3034` 对 `127.0.0.1:3034`，生产环境需独立子域），同时加上 `allow-same-origin`。框架有了真实源，隔离仍然成立。代价是开发环境与生产环境各要配一次预览源，并核对 bridge 的 `postMessage` 来源校验。
  - 不建议：直接给同源预览加 `allow-same-origin`。`allow-scripts` 和 `allow-same-origin` 同时出现在同源 iframe 上，等于取消沙箱，上游演示页的脚本能读工作台数据。

**A2 超时从挂载开始计，误报失败**

- 位置：`components/open-source-template-frame.tsx` 中 `PREVIEW_TIMEOUT_MS` 定时器在 effect 挂载时启动。
- 现象：
  - `/templates` 的缩略图是 `loading="lazy"`，屏幕外的框架还没开始请求，10 秒后就显示失败（Cursor 实测 22 张里 14 张短暂报错）。
  - 上游演示页的服务端抓取本身要 10.5 秒左右才返回 502，客户端 10 秒先到，把失败原因说成“bridge 没有回执”。
  - HTTP 502 不会触发 iframe 的 `onError`，所以真实的服务端失败永远只显示为超时。
  - 失败后点「重试」，重新载入期间是一整块白色，没有任何载入态。
- 方案：计时改从 iframe `onLoad` 开始，只计“文档已载入但 bridge 未回执”这一段；服务端 502 页面里内嵌一行脚本，向父窗口发送 `sitecraft:error` 并附原因，父组件据此显示真实原因；载入中显示骨架或细进度条，不再是纯白。失败文案改成用户能看懂的话，去掉 `bridge`、`iframe` 这类词。

**B 旧样子提示无法消除**

- 位置：`lib/site-operations.ts` 的 `set_visual_brief` 分支不清除 `legacyVisualBriefId`；`lib/site-document.ts` 的 `migrateRetiredVisualBrief` 已把旧草稿迁到 `technical-product`，所以用户再点这个样子是 no-op。
- 现象：旧 fresh 草稿不论换成哪个样子，工作台都一直显示「请换用可用样子」（Cursor 通过 `applySiteOperations` 实测）。
- 方案：`set_visual_brief` 成功写入时一并删除 `legacyVisualBriefId`；对已迁移草稿，点当前样子也视为“确认”，同样清除该字段。补一条走真实入口的回归测试：旧草稿 → `set_visual_brief` → 字段消失、撤销后字段恢复。

## 三、优化方案

优先级按项目规则排：P0 直接影响生成站好不好看、真不真；P1 影响主流程能不能顺畅用；P2 是后台和工具页。

### P0 生成站质量

**1. overlay 里的固定文案要么进槽位，要么删掉**

四个 overlay 在声明槽位之外都有写死的可见文字，逐个核对结果如下：

| overlay | 写死的内容 | 问题 |
| --- | --- | --- |
| screwfast | 首屏说明「按图加工 · 批量规格询盘 · 现场安装：待补充」 | 是 P3I 模拟包的具体事实，换任何公司都显示；而且和同一首屏的“不提供现场安装”自相矛盾。 |
| screwfast | 首屏角标「ENGINEERING / RFQ」 | 与公司无关的装饰英文。 |
| 全部 | 「资料有限时，页面保持诚实」「产品先于装饰，事实先于承诺」「少一步跳转，少一次猜测」「资料不足时保留“待补充”，不替企业补写型号…」 | 写给负责人看的方法论，访客读到会觉得奇怪。 |
| 全部 | 「04 / 资料边界」「04 / 边界」 | 同上，内部视角的分区名。 |
| screwfast、landwind | 表单下方「提交后由发布页处理。没有接通的外部邮件服务不会显示为已发送。」 | 系统说明，不该出现在访客页面。 |
| 全部 | 导航、分区编号、表单字段标签全部是中文常量 | 切到 EN 后页面一半中文一半英文。 |

方案：首屏说明、角标改成读取草稿的槽位（行业、主要行动），缺资料时整行隐藏；方法论类句子和“资料边界”全部删掉，改成访客视角的普通分区名；导航接上草稿里已有的 `navigation` 字段；表单标签和分区名按语言切换。这是开发侧改 overlay HTML/CSS，不涉及运行时模型输出 HTML。

**2. 隐藏分区后导航和编号跟着变**

- 现象：P3I 草稿隐藏了 `services`，但导航「加工方式」仍指向已隐藏的 `#process`，点了没反应，属于空链接否决项；分区编号从 01 直接跳到 03。
- 方案：bridge 在应用 `hiddenSections` 时同步隐藏指向该分区的导航项，编号按实际可见分区重新计算，或者去掉编号。

**3. “待补充”不要堆成一面墙**

- 现象：P3I 的 FAQ 六条全是「待补充 / 待补充」；FAQ 引言是写给模型的指令「只回答资料里有的交期、认证、MOQ 和售后；没有的写成待补充。」，原样显示给访客；每张产品卡都重复「认证、产能、客户、交付周期待补充」。
- 方案：
  - 标题和正文都是待补充的 FAQ 条目不渲染；全部为空时整个 FAQ 分区隐藏。
  - FAQ 引言改由生成侧写成面向访客的一句话，或者留空。
  - 同一缺口在一页里只标一次，例如在联系分区统一写“认证与产能资料待补充”，不在每张卡片里重复。
  - 这些规则写进生成侧的 operation 约束和 bridge 渲染规则，不靠 prompt 文案。

**4. 英文站不能是默认文案**

- 现象：切到 EN 后，首屏是 `lib/site-document.ts` 默认草稿里的「Built for the next standard.」，产品介绍是产品自己的说明「Import this catalog in bulk and continue editing it with AI.」，关于、联系也都是与这家公司无关的通用句。这违反“事实只能来自用户资料或待补充”。
- 方案（需负责人决定）：
  1. 生成时同时产出中英两种语言；
  2. 在用户要求英文站之前，发布页和工作台都不提供 EN 切换；
  3. 至少把默认英文文案替换成对应的待补充提示，避免展示与公司无关的内容。

**5. 页面标题和发布页 `<title>`**

- 现象：预览文档标题是 overlay 的内部名（「工业询盘首页」「灰底短路径」），发布页也没有按站点设置 `<title>`。
- 方案：bridge 应用草稿时把 `document.title` 设为公司名；发布页用 `generateMetadata` 输出公司名和一句简介。

**6. 生成站动效（克制，不做花哨特效）**

现状：四个 overlay 没有任何 `transition`，没有平滑锚点滚动，只有 2–4 条 `:hover` 规则，点导航会直接跳，按钮和卡片没有按压反馈。

方案，全部写在 overlay CSS 里，并统一放在 `@media (prefers-reduced-motion: no-preference)` 下：

- `html { scroll-behavior: smooth }`，分区设 `scroll-margin-top` 等于吸顶导航高度，避免标题被导航挡住。
- 按钮、链接、卡片加 120–180ms 的颜色、边框、阴影过渡；按钮按下时轻微下沉。
- FAQ 改用 `<details>` 展开收起，高度过渡在支持的浏览器里生效，不支持时直接展开。
- 首屏几何插画可以给一次 600ms 左右的淡入，不做循环动画。
- 不做滚动视差、逐块飞入、数字滚动这类 SaaS 落地页常见效果，工业 B2B 站用不着，也违反 `frontend-less-ai-tone`。

### P1 工作台与主流程

**7. 工作台左栏：对话被挤没了**

- 现象：1440 宽时，样子盘和色板占左栏大半高度，对话只剩两三行；375 宽时，「AI 对话」标签页里样子盘和色板几乎占满一屏，最新一条消息只露出一行。
- 方案：样子盘和色板收进一个可折叠面板，已有草稿时默认折叠，只显示“当前：工程工业 · 工程橙”一行和「换样子」按钮；新建站点、还没选样子时默认展开。对话区始终占剩余高度。

**8. 修改后在预览里标出改了哪里**

- 现状：bridge 已经回报 `appliedSlots`，但用户看不出一次对话修改具体动了哪块。
- 方案：收到回执后给这些槽位加 1.2 秒左右的描边或底色高亮，然后淡出；预览可见区外的改动，在对话消息里给一个“查看”按钮，点击滚动到对应位置。这一项直接对应“好改”，性价比最高。

**9. 移动端工作台细节**

- 预览工具栏（设备切换、中英、撤销重做、上传、发布）在 375 宽横向溢出，右侧按钮被截断。建议收成两行，或者把上传类按钮收进「…」菜单。
- 文案「样子会改变右侧预览…」「右侧预览将使用对应版式…」（`app/workspace/page.tsx:852`、`:1080`）在手机上没有“右侧”，改成“预览”。
- 预览地址栏显示「工程工业.sites.ai」，拿样子名当域名，改为站点 key 或公司名的拼音缩写。

**10. 对内信息不要摆在用户面前**

- 工作台头部的「SCREWFAST / INDUSTRIAL」「DEEPSEEK API · deepseek-flash」、分区标题「LOOK BOARD」「PALETTE」、快捷按钮「只要首页」「额外页面」「未指定页面」都是开发或测试视角。
- 方案：模板 ID 和模型名收进「…」里的诊断信息；分区改为中文“样子”“配色”；快捷按钮保留“提供公司资料”“上传产品图”“上传商品表格”，其余按对话上下文出现。

### P2 系统逻辑与后台页面
