# SiteCraft AI 产品与系统规格

状态：`approved-for-execution`；版本 v0.8；更新 2026-09-26。
依据：[已记录需求](./intent.md)、[主线](./mainline.md)、grilling Round 14（Q20–Q25）、Round 17（Q26=B）、Round 18（Q27=A）；数据删除政策按 2026-09-18 用户决定。
确认人：项目负责人。此状态批准按模块实施，不代表产品能力已实现或允许公开部署。

## 1. 产品范围

近期做内部技术 Demo，由项目负责人扮演用户，用模拟公司测试工业/B2B 主场景及相邻行业。许可和数据归属按未来自助平台考虑，但不以真实客户试点或公开部署作为近期完成条件。

主路径：资料输入 → 风格/主题选择 → 可选需求对齐 → AI 建站 → 对话修改 → 浏览器预览验证 → 用户确认。

完整“一句话建站”目标保留；本次把其前置体验（风格选择、需求对齐）提前验证。按已批准的计划分模块执行，不等待全部旧任务完成才验证成品质量。

页面规划优先级已确认（Q18）：

1. 用户明确要求的页面、界面和单页/多页结构优先。
2. 用户未列页面时，模型根据行业、目标、资料与主要行动规划页面，并在生成前显示计划。
3. 前两项仍不能确定时，才使用“首页 / 产品或服务 / 联系”作为默认方案。

默认方案不是三页上限。需支持用户要求和模型规划的不同页面集合及跨页导航；模板原生有页面不等于 SiteCraft 已支持。当前能力不匹配时明确说明和规划所需实现，不得默默缩成单页或固定三页，也不编造已经接通的后台业务。

## 2. 面向用户的风格/主题选择

用户选择的是效果，不是 Skill、模型或提示词版本。风格入口与“需求对齐”开关相互独立；不启用对齐也能选风格，或者保留“AI 推荐”。

首屏展示少量**样子盘**，每张卡包含名称、预览示意、这类模板适合什么内容。张数按已有本地快照来，不锁死四张或六张。行业/内容结构来自企业资料，不和样子卡抢位置。

当前可挂卡的样子见 [MAP.md](../../.project-map/MAP.md) 的 Notes「现状」：明亮产品、工程工业、蓝白目录、灰底短路径有 kit，只有这四个样子背后的模板能新建站点；深色产品（`fresh`）没有 kit，和其他开源模板一样在模板页只作参考（T-044），要不要补 kit 另开决定。没有对应开源快照的样子（例如像素风）不上卡。代码里若仍按「工业/外贸」1:1 绑模板，视为待改的过渡，不是规格。

### 色彩集与色板（2026-09-24 确认）

- **色彩集**是给用户选的配色方向，首批 6 套：青花瓷、石墨工坊、工程暖橙、铜锈、松石、莫兰迪。不提供马卡龙、荧光笔、波普这类不适合企业官网的集合。
- **色板**是某个样子里某套色彩集的具体 token（背景、表面、正文、次文字、强调、强调深、边框、浅底）。6 套 × 4 个样子 = 24 套色板，ID 为 `<样子前缀>-<色彩集>`；正文、次文字（对背景和表面）与按钮白字（按各 overlay 主按钮实际使用的 token）都 ≥ 4.5:1，由测试检查。每个样子有默认色彩集：工程工业为工程暖橙，其余为青花瓷。旧的 16 个色板 ID 在读取草稿时换成最接近的色彩集。
- 换色彩集不改版式和内容，走白名单 operation，可撤销。色卡用「当前样子 + 该色彩集」的真实颜色显示。
- 自定义品牌色：用户输入主色或从上传的 Logo 取色，由开发侧固定规则生成整套色板并检查对比度；过浅强调色自动压暗并向用户说明；色板作为可撤销 operation 写入草稿，预览优先读取它。不由模型写 CSS。排在 6 套预设之后实现。
- 样子按行业给「推荐」并附一句理由，其余样子仍可选，不按行业限制。

主题 ID → 版本化设计意图（`visualBrief`）→ 同一视觉族里的模板与区块筛选 → 受控生成。内部审美规则当前指定为 `sitecraft-frontend-less-ai-tone`，用户界面只显示样子名称。

预览示意标注为示意；只有模板和受控操作确实能落地的能力才标为可生成。没有合适素材或模板时说明缺口、给替代候选，不能假称已应用。

## 3. 内嵌的需求对齐（新建站点默认开启）

### 3.1 交互

- 新建站点（还没生成过）默认开启需求对齐；已生成站点的修改默认不走完整访谈，只在重大变化时确认。输入框上方的「需求对齐」开关可关闭，开关上写明「开」「关」，按当前会话保存，不做账户全局开关。（2026-09-24 确认，取代「建议默认关闭」）「还没生成过」指草稿历史里没有模型生成的修改。
- Agent 根据已经提供的资料，只询问会改变站点结果的缺口，不固定跑完整问卷。形态参照 harness 向用户提问：一张卡一次 1–4 题，最多 3 轮。第 1 轮通常包含主要行动、页面、样子、配色；样子排在配色前，配色按所选样子显示。还没生成过的站点即使资料已经齐全，第 1 轮也要问样子和配色；这两题由服务端按目录生成，配色选项只来自色彩集（卡上放 4 套，其余在「配色」按钮里），模型只能推荐样子。
- 每题 2–4 个稳定选项，推荐项标「推荐」并附一句理由，允许「其他，我来写」。题目分单选、多选；整张卡全部答完后一次提交，不再要求发送一段聊天文本。手机上改为底部抽屉逐题作答（上一题/下一题），只显示当前题，提交语义不变；刷新后仍按服务端答案恢复选择。
- 提供“交给 AI 推荐”或跳过非关键偏好。缺少事实/授权不能通过选“推荐”编造；允许先出带缺口提示的预览，关键发布条件仍需补齐。
- 回答后在聊天历史中显示问题与所选答案，Agent 自动继续下一步。用户不必重新发指令、不必复制问题或说“继续”。
- 关闭对齐模式只关闭完整需求访谈，保留风格入口、必要的安全/事实澄清和发布确认。关闭时已选答案保留；待回答的非必要问题取消，不继续强制追问。
- 全站生成前展示简短需求摘要和模板/方向确认；确认后生成。修改既有站点时，只确认本次重大变化，不每轮重问完整需求。

### 3.2 连续会话，不依赖一直运行的模型请求

可恢复状态建议：`collecting → awaiting_user → collecting → awaiting_confirmation → generating → editing`，另有 `cancelled` 和失败状态。对齐关闭直接走已有生成/编辑入口及必要确认。

模型每次只运行到“需要用户信息”为止：保存待回答问题后结束当前模型调用和事件流。页面保留等待中的同一任务；用户回答时以相同 `conversationId` 恢复。这满足对话连续性，不依赖浏览器标签一直开着，也不在等待期间持续计费。

对用户展示问题、选项和结果，不保存或展示模型的完整内部推理作为工作流状态。

### 3.3 最小会话与接口扩展

优先扩展现有 Chat API 和会话存储，不创建独立 alignment 服务、任务队列或第二套聊天接口。

- 会话持久化 `alignmentEnabled`、当前目标、已确认答案、一个待回答问题组及状态版本。
- 待回答问题至少有 `questionId`、`questionRevision`、选项 ID、显示文案、对应需求字段；用户只可提交当前服务端实际发出的 ID。
- 回答请求携带会话 ID、问题 ID/版本、所选 option IDs 和可选补充文本，不依赖模型从按钮标签猜用户选择。
- 复用 `clarify/status/done` 等已有事件语义；问题卡片作为结构化 clarify 载荷扩展，具体 Zod 形状在实现前与现有调用者对齐。用户等待不伪装成生成完成。
- 待回答状态保存成功后才发卡片；刷新通过受会话归属约束的读取方式取回。先实现实际工作台调用者，再定历史读取接口。
- 一张需求对齐卡可携带 1–4 个独立问题；每题使用独立 `questionId` 和选项，客户端一次提交 `selections`，服务端逐题校验后原子保存答案并继续同一会话。
- 每题选项数量为 2–4，可带 `recommended` 标记；工作台显示推荐项并允许“其他”输入，选择“其他”时必须随该题提交 note。单题卡也走同一批量提交协议。
- 规划器输出允许直接返回 `questions` 数组；服务端将首题归一化为兼容字段，不能因缺少重复的顶层单题字段而把有效问题卡判成 provider_error。规划器不输出配色题，只可用一道样子题推荐样子，另外最多 2 题；输出长度上限要容得下这张卡。
- 规划器 invalid_output、回答被截断、超时和连接失败必须明确返回给当前请求并允许重试，不能静默替换成内置样子问题。
- Chat API 对规划失败返回 `retry_alignment` 与当前错误状态，不创建或替换待回答问题。
- 测试夹具中已明确标记的恢复/延迟哨兵走 deterministic alignment 入口，不调用规划器；真实请求仍遵循上一条失败契约。
- 新建站点请求的模板通过初始化 operation 写入草稿的 `visualBrief`、模板和页面计划；默认站点名与公司名使用中性缺口文字，不使用演示品牌。
- 创建接口返回的草稿已经包含上述初始化 operation 结果，后续需求对齐以该模板和设计意图为上下文继续。
- 从模板页进入工作台（`/workspace?template=<id>`，不带 `site`）就是新建站点：工作台调用创建接口，再把地址换成 `?site=<新 id>`，刷新时打开同一个站；不改任何已有站点的模板。只有四个样子背后的模板（forge、screwfast、landwind、tailwind-landing）能这样新建；其他开源模板在模板页只作参考，没有进入按钮，直接打开地址时工作台说明不能生成，不新建也不打开别的站点。
- 重复点击/提交不能重复推进或重复 commit；过期问题、多标签页冲突、错误会话 ID 明确拒绝，并展示最新可回答状态。
- 等待和回答只修改会话资料，不直接修改站点草稿。确认后的站点变更仍走 `commitOperations`，并检查草稿 revision；换模板/已修改草稿会使旧确认失效。
- 如果已 commit 但流中断，恢复时先读取真实 revision/结果，不再执行同一份生成操作。

### 3.4 工作台布局与主题（2026-09-24 确认）

- 布局：预览居中，对话停靠右侧；样子盘和色板不再占左栏，改为对话里的提问卡片和输入框上方的「样子」「配色」按钮。平板上对话为抽屉；手机上「对话 / 预览」切换，需求对齐用底部抽屉逐题作答；375 宽预览工具栏的操作按钮都保持在视口内。375 / 768 / 1440 都要成立。
- 主题：工作台有深、浅两套，默认跟随系统；另可从 6 套色彩集里选工作台强调色。这是用户的界面偏好，与正在编辑的站点配色独立，不跟随站点变色。
- 顶栏横跨全宽：返回、站名、保存状态｜预览宽度、中/EN｜撤销、重做、发布、删除。输入框上方一排操作，分三组：需求对齐开关｜样子、配色｜公司资料、上传产品图、商品表格（次要样式），按钮都常显、高度桌面 ≥ 36px、手机 ≥ 44px；需求对齐不藏在「+」菜单里。不放开发自测用的提示句。需求对齐卡打开或新一轮到来时，对话滚到卡片顶部。出错时只有一个错误框，下面一行「已保存的草稿没有变化，可以直接重试。」
- 进行中的工作在对话里显示当前一步和步骤列表（例如「读资料和要求，规划页面和要问你的问题」「生成修改」「校验并写入草稿」），步骤只按服务端状态前进；完成或失败后淡出，失败时留下错误说明。
- 动效只用 `transform` / `opacity`，150–300ms：需求对齐卡选中、换题、提交后收起，手机底部抽屉进出，平板对话抽屉开合，面板和对话框出现，预览刷新时页面轻微变暗再恢复（已显示过的页面不再被整块遮住）。`prefers-reduced-motion` 下全部不播。
- 深浅两套主题、6 个强调色下，工作台全部文字（对话、需求对齐卡与抽屉、样子/配色面板、历史、对话框、空状态、错误、预览工具栏）对比度 ≥ 4.5:1，由 `tests/workspace-dark-contrast.test.ts` 在 1440 / 768 / 375 量出。界面上不出现英文开发标签。
- 应用一次对话修改后，预览区显示由实际 `appliedTargets` 生成的中文改动落点摘要（例如「产品介绍」「优势第 1 项标题」）；摘要只用于工作台反馈，不写入发布页，也不向用户暴露字段路径。改动标记只来自这次修改的 change set（服务端的 `appliedTargets`）；预览桥回报的 `appliedSlots` 是页面此刻的实际落点（包括按样子默认布局挂上的区块），只用来确认这次的落点已出现在页面上，不用来生成改动标记。
- 对话修改没有改动草稿时：系统拒绝了模型要的修改（例如资料不够的布局、用户没要求的换样子），回复只有原因「未修改：……」（去重，用「；」连接）；模型本来就没有可应用的修改时，才显示「模型没有生成可应用的内容差异，草稿和模板均未修改。」和它的摘要。
- 刷新后恢复需求对齐时，如果上一次生成或保存失败，对话里先说出原因，和当时的提示一样（例如「这次生成被截断，没有改动草稿。 可以直接重试；已保存的问题和答案仍可继续。」），问题卡还在就可以直接重新提交。只显示错误目录里的说法，其他记录显示「需求对齐没有完成，草稿没有修改。请读取当前状态后重试。」。
- 原型：[SiteCraft 工作台改版原型](https://claude.ai/artifact/BG2wuABfaVQTLPRaBWzUct)。负责人选定：方向 B 的布局与手机逐题抽屉，深浅两套主题；原型不是像素规格，实现以本节为准。

## 4. 模板、Skill 和设计契约

### 模板范围

当前已存在的模板继续使用并重新分类，同时寻找不同主题、内容密度和业务场景的开源候选。此前 `forge/atlas/kindred/signal/lonestone` 是存量优先检查名单，不再限制候选数量或禁止替换。

当前 iframe + `lib/template-adapters/preview-bridge.ts` 是**唯一**预览引擎。开源模板、区块、样式是移植进 SiteCraft 区块库的素材，不整页挖空填词，也不把未经移植的外部区块直接拼进页面。原生 React/shadcn 系统性改造仍留后续决策门。

### 区块库、设计 token 与站点样式（2026-09-29，T-048 / T-051）

- **区块库**放在 `lib/blocks/`：每个区块变体是一段开发侧 HTML（根节点 `data-sc-block="<区块>" data-sc-variant="<变体>"`，可改样式的部位标 `data-sc-part`），HTML 和 CSS 在 `lib/blocks/fragments/`（只在服务端用），配一份数据清单（`lib/blocks/catalog.ts`）：区块、变体、读哪些草稿字段、槽位（沿用 adapter 的 `selector → target` 写法）、预览桥自己渲染的固定节点、部件名、最少资料条件（例如「参数对比」要 2–4 个产品共有 ≥3 项参数）。清单是可审查数据，不存可执行 JS；区块库样子的 adapter 由清单生成（`lib/blocks/adapter.ts`）。结构可参考 HyperUI、Meraki UI（MIT，改写成自己的类名并保留许可声明）；它们的图片、图标不用，Preline 不用；第一版不用图标。
- **样子 = 设计 token + 默认变体组合**。token 全部是 `--site-*` CSS 变量（和现有色板同一套命名）：字体组合、字号比例、圆角、间距密度、分割线、表面处理；颜色仍来自色板。一个样子的 token、版面顺序和默认变体写在 `lib/blocks/looks/<样子>.ts`。工程工业的 token 是容器宽与边距、区块间距、h1/h2 字号（另有大标题布局用的展示字号）和两种分割线；字体和圆角仍随色板。区块 CSS 用两个断点：≤900px、≤480px。
- **组页**：服务端按样子把区块库拼成整页骨架（`lib/blocks/compose.ts`），走现有的模板静态文件路由，不再依赖旧的整页 overlay。每个区块放一份默认变体的实体，每个变体（含默认）另有一份 `<template data-sc-template="<区块>:<变体>">` 原件。预览桥写槽位之前先挂载：从 `<template>` 克隆草稿选的变体（没选就用样子默认）换掉现有实体，已经是这个变体就不动；再照旧写槽位、处理显隐。`<template>` 里的节点不在文档树里，所以每个区块任何时刻只有一个实体，写入仍唯一命中声明节点，预览引擎还是一个。四个样子均由区块库拼页：工程工业（模板 `screwfast`）、明亮产品（模板 `forge`）、蓝白目录（模板 `landwind`，默认产品布局为目录行）、灰底短路径（模板 `tailwind-landing`）。子模块和模板页里的参考条目保留，模板 id 仍保留。
- **区块编排**沿用草稿现有的 `sectionOrder` / `hiddenSections`，新增 `blockVariants`（区块 → 变体）：没有记录的区块显示样子的默认布局，默认布局不写进去；不绑样子，换到尚未迁移的样子时保留、不生效；读草稿时丢掉清单里没有的区块或布局，旧草稿没有这个字段就是全部默认。新 operation 只有 `set_block_variant`（`variant` 为 null 表示改回默认，inverse 是前一个值）。检查按整批操作做完后的草稿做，布局和它要的资料谁先谁后都行，撤销也一样：这一批要的布局资料不够（或当前样子还没迁到区块库）时整批拒绝，用页面上的说法说明原因，不静默换别的；之前选好的布局因为这一批的资料变化不够了，就在同一批里改回默认，可撤销、改动标记显示「产品布局」这类名字，原因（「……，产品改回产品卡片。」）写进这次修改的摘要。
- **模型选布局**：只在区块库样子的提示里给出第 17 条 `set_block_variant` 和「可选布局」清单（由清单生成：每块的布局 ID、名字、默认、要什么资料），并要求按资料生成整站时为每一块各给一条（选默认也写出来）。模型的布局请求先按它这次其他修改做完后的草稿检查：资料不够的丢掉，原因（「……，产品仍按产品卡片显示。」）接在摘要后面，全部被拒时原因就是摘要；会导致改回默认的也写进摘要。摘要不超过 400 字，原因保持完整。模型每次最多 24 条 operation；需求对齐的方案另加样子、色彩集和一张产品图，最多 27 条。需求对齐生成时先在内存里套上卡片里选的样子和色彩集再调模型，模型拿到的是这个样子的布局清单，校验也按这个样子；草稿只在确认后经 `commitOperations` 改。
- **工程工业的布局**（用户面前叫「布局」；★ 为默认，默认不需要额外资料）。清单里 `render` 是预览桥怎么填这个变体，`requires` 是最少资料条件，由 `lib/blocks/requirements.ts` 按预览桥的渲染口径计数：缺口（待补充 / To be provided）一律不算，产品只算访客看得到的。
  - 首屏：★左文右图（有产品照片放照片，没有放参数铭牌）；大标题加参数条（大标题、按钮行和参数条在内容宽度里成一组，和标题左对齐：参数条在按钮行下方约 32px，浅色底（`--site-surface`）加 1px 边框、顶部 2px 强调色细线，标签小号次要色、数值加粗；1440 一行四项，768 两列两行，375 两列；标签在空格处换行，数值按参数值的断行规则换行；标题比左文右图大、比 2026-09-30 之前小一档（`--site-h1-display` 最大 64px）；没有照片也显示；要 ≥3 项带数值的产品参数，参数条最多 4 项，多个产品时每个取前 2 项）。
  - 产品：★产品卡片；按类别分组（每个类别一组卡片，没写类别的排在最后的「其他产品」；要 ≥2 个产品类别且有一类 ≥2 个产品）；参数对比表（上面每个系列一张说明卡，只有它有的参数收起放在卡里；下面一张表，行是每个系列都有且都有数值的同名参数，列是系列；手机上每行变成一块，每个值标出系列；要 2–4 个产品共有 ≥3 项这样的参数）。
  - 询盘：★左右布局（邮箱、电话）；联系条（标题和说明一行，下面一条深色联系信息：邮箱、电话、地址里有值的才显示，再下面整宽表单；要其中 ≥2 项）。
  - 合作方式（流程，只有一种排法）：最多 6 步，空条目不显示，步号按显示出来的条目连续编（T-059）；模型最多写 6 步，提示里写明当前样子显示几步。
  - 常见问题（只有一种排法）：最多 6 条，和草稿自带的条数一样（T-059）；有问有答的条目先显示，空条目不显示，一条都没有时整块不显示。模型提示里写明当前样子最多显示几条（由样子声明的条目数算出：工程工业 6、明亮产品 6、蓝白目录 6、灰底短路径 6），资料里有几组问答就写几条。整站生成时模型用一条 `replace_cards`（`section` = faq / services / features，带完整条目列表，inverse 是原来的整组）写完一组，不再每条问答占一条修改：之前注塑生成总是用满 24 条修改上限，5 组问答只写进 3–4 组；只改其中某一条时仍用 `update_card`。模型写的常见问题最多 6 条，多出的不写并说明；标题和正文都缺的条目不写，整组都缺时不执行（不会误清空）；草稿本身每组最多 12 条，撤销能放回任何已有的整组。
  - 参数值在所有布局里都换行显示全，不截断：只在空格和 / + – 、 之后换行（「/」只在两边的片段都至少 3 个字符时才可换行，片段以空格和「/」分界，所以 r/min、G1/4、N/m 不断开，S136/H13/NAK80、PA6/LCP 可以），不在一个词或一串汉字中间断开，只有单个片段比格子还宽时才强制断开（`word-break: keep-all` 加 `overflow-wrap: anywhere`）。预览桥写参数值时在这些位置加零宽断点（U+200B；`<wbr>` 元素在不换行时也会让字形移位），草稿里的值不变，访客复制时去掉断点。默认产品卡片在桌面上值在自己的格子里换行，手机上值占一行、参数名换行，值超过一行的七成才换行。值为缺口的参数格不显示；界面文字随页面语言。参数值可以是数字/单位/型号字符串（两种语言相同），也可以是 `{zh,en}`；带中文或中文全角标点的值必须有英文，英文缺口在英文页不显示，旧草稿的字符串值照原样读取、不自动翻译。
  - 邮箱只在 @ 前后换行，不在「-」处或名字中间断开（`inquiry@` / `p3i-sim.test`），询盘、页脚的联系邮箱和写在句子里的邮箱（例如询盘说明「规格发到 catalog@p3e-sim.test」、常见问题）都一样：预览桥写文字时在邮箱的每个「-」后加不换行连接符（U+2060）、在 @ 两侧加零宽断点，某一段本身比整行还宽时才强制断开（`overflow-wrap: anywhere`）；草稿、mailto 链接和访客复制都是原样。
  - 发布页检查（`scripts/check-published.mjs`）会把看不全的文字判为失败：超出自己格子或卡片的文字、被省略号或行数截断的文字、被裁剪的文字，以及不在 @ 处换行的邮箱（检查脚本 `scripts/visitor-text-fit-scan.js`，测量时会展开收起的参数表）。
  - 发布页检查还核对资料事实是否落到页面（`scripts/published-facts.mjs`）：从草稿（不问渲染器）按页面语言取出每个显示的产品的名称、说明和参数（参数名与非缺口的值）、样子放得下的常见问题和合作方式条目、应用行业和加工能力的条目与正文、认证名称、询盘邮箱和电话，在访客能读到的文字里逐条找（`scripts/visitor-readable-text.js`：只取画出来的文字节点，展开收起的参数表和问答，去掉换行断点），找不到就判失败并列出缺了哪些。`englishReady` 草稿的英文页三档也检查，参数值格里不得出现汉字。草稿隐藏的分区和缺口不算；认证的正文不算（工程工业把认证做成徽章，只显示名称和状态）。
  - 常见问题、合作方式、优势在页面上的条数固定、按序号写入。页面先显示有标题或正文的条目（按草稿顺序），再轮到空条目：新草稿自带空条目，模型用 add_card 加的条目排在它们后面，按序号写入时页面只显示空条目、真的问答到不了页面。每个位置写入的是那一条自己的序号（例如 `faq.items.6.title.zh`），在工作台点它、确认修改都落在那一条上；放不下的条目改了之后，工作台提示「当前样子没有位置显示：常见问题第10项标题」这类说明。
- **站点样式**（负责人 2026-09-29 选 T-051 的做法 A；2026-09-30 决定只按用户要求使用）：模型输出结构化规则，不写 CSS 文本：`{ block, part?, media?, declarations: { 属性: 值 } }`。新 operation `set_site_style` 整份替换规则表，inverse 恢复前一份。整站生成和需求对齐不输出 `set_site_style`，也不计算或提供建议方向；用户在后续对话里明确提出外观或版式要求时，提示才展示工程工业的规格为主、目录为主、工厂实力方向菜单，并允许选择一个方向配方或追加规则。校验按 [T-051 调研](../research/区块素材与CSS校验调研-2026-09-29.md) §3.3 的白名单：区块/部件只能是清单里有的；`media` 只能是项目断点；属性按组放行；值里禁一切字符串、反斜杠、非 ASCII、`url()` 等资源函数、`!important`；`content`、`position`（除 static/relative）、`z-index`、`overflow*`、`opacity`、`transform`、`list-style*` 等整条禁用；序列化后 ≤ 8 KB、≤ 40 条规则、≤ 200 条声明。追加规则是整份 operation 的一部分。页面 CSS 由 SiteCraft 自己的序列化函数从规则表生成，加 `[data-sc-block=…]` 前缀，不透传模型原文；区块库 CSS 放进 `@layer sc-blocks`，站点样式放进其后声明的 `@layer site-style`，保证样式可以覆盖区块库，同时不能触及缺口和显隐保护。提交检查在中文三档及有英文页时的英文三档运行；只拒绝样式带来的新增溢出、重叠、槽位不可见或对比度不足，撤销/重做不重查。
- **三档检查**：`set_site_style` 提交前，在常驻的无头 Chrome 里（沿用 `scripts/check-published.mjs` 的原生 CDP 做法，不加浏览器依赖）按 375 / 768 / 1440 各渲染一次候选草稿，和不带新样式的基线比：新增横向溢出（`scrollWidth` 和元素右边界两种都查）、新增文字框重叠、槽位文字被藏，任何一项出现就拒绝这次修改，并告诉用户哪一档、哪个区块出了问题。候选草稿在内存里渲染，不先写修订再撤回。检查起不来（没有 Chrome）时报错，不跳过。

模板元数据只保留有消费者的字段：来源版本/代码许可/独立素材授权，行业与页面类型、语言、素材要求、主题倾向、支持的内容槽位及限制、已验证状态。先排除不兼容来源，再比较风格。

### 运行时归属

- `visualBrief`：用户选定的受众、主要行动、语言与设计意图；同一份数据服务模板匹配和生成。
- 模板能力说明/slot map：可编辑内容到真实页面元素的映射，覆盖和不支持项必须真实报告。声明槽位是落点工具，不是「未声明就原样留下」的成品许可。
- 素材计划：引用已有素材 ID、来源、许可、裁切/比例和事实属性，不能另建未经授权的素材镜像。开源 HTML/CSS/token 作为素材准入时，图片、字体、图标仍须单独核验。
- 白名单 operations：把被支持的文字、图片、主题变化转成可撤销修改。未确认的设计预案先存会话，持久化到站点时也不能绕过 commit。
- 双语文案使用一条 operation 携带 `{zh, en}`；英文缺口写 `To be provided`。草稿的 `englishReady` 由实际写入非缺口英文的 operation 设置，发布页按该数据标记决定是否提供 EN，不通过与默认句子比较推断。
- 商品类别属于双语文案，随商品 operation 携带 `{zh,en}`，发布页和工作台按当前语言读取；旧单语类别只作为旧草稿兼容读法。行业同样是双语字段。公司名和站名只保存资料里的原文（模型给出的译名不采用），资料没有时保留中性名称。认证状态按页面语言显示（已有 / Certified、认证中 / In progress）。
- 所有会写入双语英文的 operation（包括卡片更新）都必须把 `englishReady` 的前值纳入 inverse，撤销后恢复英文开关状态。
- 模块选择：只在同一 `visualBrief` / 模板族内决定使用哪些已准入区块。跨模板或跨站 HTML 拼接不是合法 operation。
- 目录类内容：产品可带规格参数表；站点可有应用行业、加工能力、认证状态三个目录区块，均通过 operation 写入。认证状态分为已有、认证中、待补充；访客页只显示已有和认证中，全部待补充时整块隐藏。产品图片带署名信息，CC-BY 类许可在访客页署名。
- 询盘入口：询盘表单是站点的主要行动，不属于资料事实，不受缺口规则影响；资料没写询盘文案时用界面文字作标题。
- 新草稿不含演示文案：公司事实字段是「待补充 / To be provided」，标题是中性界面文字；说明类字段（区块引言、询盘正文、首屏副标题、关于正文）整段是缺口时整句不显示。新草稿也不带商品；访客页上商品区没有可显示的商品时整块隐藏，指向它的导航和按钮一起隐藏，工作台预览里保留「产品资料待补充」提示。
- 没有草稿的页面（模板页缩略图、模板预览页）：工程工业页面按同一缺口规则显示，没有内容的问答、步骤和联系行不显示，整块都空的区块连同指向它的导航和按钮一起隐藏，页脚的产品一栏也不显示，只剩页头、首屏的询盘按钮、询盘表单和页脚。有草稿时（包括工作台预览）按上面的规则。

不为了文档名称同时持久化 DESIGN.md、page-plan.json 和 visualBrief 三套重复数据；先明确具体消费者再选字段。

### Skill 使用

Impeccable、UI UX Pro Max、Marketing Skills 等仍是候选材料，不是已安装能力。审美主流程的内部实现指定为项目 Skill `sitecraft-frontend-less-ai-tone`（文案层 + 样子层，模型只能写受限的站点样式；规范在 `skills/sitecraft-frontend-less-ai-tone/`，运行时 `sitecraft-frontend-less-ai-tone@0.3.1`）。每次生成只走这一条审美主流程，规范检查按需要调用。用户选项不出现 Skill 名称。Jiro 免费区提示词可学写法，不得当生产 prompt。

运行时必须显式加载经审查且固定版本的规则/工具，并验证输出被使用；不把本地 IDE 安装 Skill 当作 DeepSeek 已自动读取。优先复用已有浏览器能力，不为截图再引入第二套工具。

代码优先选择允许生成器再分发的 MIT/Apache 来源；图片、字体、图标等按各自许可独立审查，不能把模板代码的 MIT 标签当成全部素材授权。

## 5. 质量与对照实验

使用 3 份独立准备的模拟企业资料 × 4 个流程组，共 12 个结果；资料明确标为测试事实，在提示词冻结后提供，不能把答案嵌入生产 prompt。

建议资料分别覆盖工业制造、外贸目录和专业服务；三者是对照样本，不改变工业/B2B 的首批产品重点。所有组固定模型配置与可用素材，C 组允许按预定规则选模板，记录这种变化，不能声称是纯 Skill 收益。

A 当前默认流程；B 增加单一审美指导；C 增加资料驱动的模板选择/设计意图；D 增加真实截图审查与最多两轮局部修复。如果现有操作只能改文案，B 的实验能力边界也必须写明，不能声称测了完整视觉生成。

验收证据：

- 提问不改稿、非法目标不误写、回答后恢复且只提交一次。
- 用同一公司资料换风格，验证真实布局/字阶/图片处理或受控主题变化；仅主题名称/摘要变了不算有效。
- 使用资料驱动检查 + 人工核对关键数字、认证、评价、案例；不承诺仅用关键词规则证明所有语义事实。
- 浏览器在 375/768/1440 CSS 像素及拥挤断点检查，覆盖菜单、焦点、表单错误和结果；表单成功提示不是收件证据。
- 独立审核 agent（不是做这项工作的 agent）隐藏分组、打乱展示，评价品牌差异、行业适配、可读性、图文一致和行动清晰；负责人不做盲评。做工作的 agent 自评是探索证据，不能外推客户满意度或转化率；评分阈值先校准。
- 盲评界面隐藏流程组、核验记号、默认对照和冻结版本等内部标记；质量基线的冻结 HEAD 由服务端运行时读取，不在界面写死。

## 6. 数据与执行边界

DeepSeek 为当前提供方，请求模型名为 `deepseek-flash`（对话与视觉同一条）；质量优先；保留有限超时、用户取消和失败说明。外发资料最小化，密钥只在服务器环境变量内，不送入 prompt、日志或浏览器。

`deepseek-flash` 默认开思考模式，推理 token 计入 `max_tokens`（实测一个 8192 的回答全是推理、没有内容）。为保住质量，思考模式保持默认，预算按实测放宽：整站生成（结构化修改）至少 65536、每次最多等 300 秒（实测不设上限时 13.7K–22.7K，其中推理 11.2K–18.7K，57–95 秒；上限 32768 时注塑仍有一次用到 32761、其中推理 31191，被截断；现阶段成功率优先，不设成本和等待时长指标）；需求对齐规划 8192、90 秒（实测 2.6K–3.2K、13–16 秒）；看图和预览审查仍是 800（看图实测 435–495）、每次 45 秒。回答不是 JSON、格式不对或服务端 5xx/429 时仍再试一次，但两次合计有上限：整站生成 360 秒、需求对齐规划 150 秒，第二次只用剩下的时间，一点不剩就不再发请求，告诉用户第一次的失败原因。四个调用（需求对齐规划、整站生成、看图、预览审查）的回答达到上限时都不再重试，直接告诉用户「这次生成被截断，没有改动草稿。」（错误码 `truncated`，看图和预览审查的接口也用错误目录的这句），规划这一步说「需求对齐规划被截断，原需求没有修改草稿，可以重试。」。

模型调用每失败一次（包括随后重试成功的那次），服务端记一行日志 `[sitecraft] DeepSeek call failed {…}`：哪个调用、第几次尝试、类别（`timeout` / `http` / `network` / `parse` / `schema` / `truncated`）、HTTP 状态、这次尝试的耗时、上游 trace id（`x-ds-trace-id`），收到回答时再加结束原因和 token 用量（输入、输出、其中推理），网络错误加错误码，格式不对（`schema`）时加出错字段的路径和问题类型（例如 `operations.0.value:invalid_union`，最多 6 条，不带值；模型自己编的键写成 `?`）。日志不记密钥、资料、prompt、模型输出和上游错误原文（它可能复述请求）。用户看到的提示仍按错误码给出。
