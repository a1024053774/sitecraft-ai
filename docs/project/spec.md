# SiteCraft AI 产品与系统规格

状态：`approved-for-execution`；版本 v0.9；更新 2026-10-07。
依据：[已记录需求](./intent.md)、[主线](./mainline.md)、[T-127 新路线决定](../../.project-map/tickets/T-127-route-model-writes-site.md)、grilling Round 14（Q20–Q25）、Round 17（Q26=B）、Round 18（Q27=A）；数据删除政策按 2026-09-18 用户决定。
确认人：项目负责人。此状态批准按模块实施，不代表产品能力已实现或允许公开部署。

## 1. 产品范围

近期做内部技术 Demo，由项目负责人扮演用户，用模拟公司测试工业/B2B 主场景及相邻行业。许可和数据归属按未来自助平台考虑，但不以真实客户试点或公开部署作为近期完成条件。

主路径：资料输入 → 风格/主题选择 → 可选需求对齐 → AI 建站 → 对话修改 → 浏览器预览验证 → 用户确认。

完整“一句话建站”目标保留；本次把其前置体验（风格选择、需求对齐）提前验证。按已批准的计划分模块执行，不等待全部旧任务完成才验证成品质量。

页面规划优先级已确认（Q18）：

1. 用户明确要求的页面、界面和单页/多页结构优先。
2. 用户未列页面时，模型根据行业、目标、资料与主要行动规划页面，并在生成前显示计划。
3. 前两项仍不能确定时，才使用“首页 / 产品或服务 / 联系”作为默认方案。

默认方案不是三页上限。需支持用户要求和模型规划的不同页面集合及跨页导航；模板原生有页面不等于 SiteCraft 已支持。当前能力不匹配时明确说明和规划所需实现，不得默默缩成单页或固定三页，也不编造已经接通的后台业务。

## 2. 面向用户的风格选择

新建站点走 T-127 的站点代码路线。用户选择「帮我选」「精密工程」「现场实拍」，并设置「版式：规整 ↔ 大胆」「信息：疏朗 ↔ 紧凑」两个滑杆（1–10）。偏好与结构化选项保存在同一会话和站点记录中，刷新恢复。选择「帮我选」时模型依据资料选风格并给理由；选定风格时模型不能替用户改选。

当前 T-128 不做风格卡、缩略图或扩充风格库。用户确认页面大纲之后才写站点代码；大纲与正文只生成中文。

页面骨架版式卡在 `skills/site-code-core/SKELETONS.md`，每次规划与写页随核心规范加载。规划时随机打乱卡片并记录实际顺序，模型返回顶层 `skeletonId`、`skeletonReason`；编号必须是现有卡片或 `custom`，拼错时以简短中文拒绝。理由说明主选的资料依据、首屏与后续节奏，并点名次合适那张及不选原因；不按行业或公司分配。产品族入口仅适用于至少三个差别明显的系列、且资料以分类目录为主。每页 `outline` 返回最多六个短句，服务端以分号连接为大纲文字，最大长度仍低于原 800 字上限。选择整理为 `skeleton: {id, reason}`，与 `skeletonOrder` 一同保存、刷新并传给写页；历史大纲没有记录时不补造。版式卡不是事实来源，所有站点仍经唯一提交入口检查存版。评估轮次的 `private/case-N/code-site.json` 保留大纲，可据其选择统计分布。

### 旧站点的色彩集与色板（2026-09-24 确认）

以下样子、色板和 operation 规则只适用于仍保留的区块库旧站点；T-128 不改变这条路径。


- **色彩集**是给用户选的配色方向，首批 6 套：青花瓷、石墨工坊、工程暖橙、铜锈、松石、莫兰迪。不提供马卡龙、荧光笔、波普这类不适合企业官网的集合。
- **色板**是某个样子里某套色彩集的具体 token（背景、表面、正文、次文字、强调、强调深、边框、浅底）。6 套 × 4 个样子 = 24 套色板，ID 为 `<样子前缀>-<色彩集>`；正文、次文字（对背景和表面）与按钮白字（按各 overlay 主按钮实际使用的 token）都 ≥ 4.5:1，由测试检查。每个样子有默认色彩集：工程工业为工程暖橙，其余为青花瓷。旧的 16 个色板 ID 在读取草稿以及迁移 history/future 的 `set_palette` 正向、逆向 operation 时，按下线时登记的同一份映射换成最接近的色彩集（例如 `industrial-minimal-gray → industrial-graphite`）；当前提交仍只接受现行 ID。
- 换色彩集不改版式和内容，走白名单 operation，可撤销。色卡用「当前样子 + 该色彩集」的真实颜色显示。
- 自定义品牌色：用户输入主色或从上传的 Logo 取色，由开发侧固定规则生成整套色板并检查对比度；色板同时提供强调文字色，按钮、规格块、次按钮、链接和标签的实际落点都检查对比度；过浅强调色自动压暗并向用户说明；色板作为可撤销 operation 写入草稿，commitOperations 提交边界会复用同一套校验，失败不改变草稿，预览优先读取它。不由模型写 CSS。排在 6 套预设之后实现。
- 需求对齐规划器按资料呈现的业务形态给样子和色彩集「推荐」并各附一句事实理由：结合产品系列和参数选型、出口/内销成交路径、工厂能力与资料厚薄判断，不做行业标签到固定样子的硬映射。提示逐项说明四个区块库样子的实际 token、默认区块和适合的业务形态；`question` 和 `ready` 都必须返回结构化 `recommendation`（`styleId`、`styleReason`、`colorSetId`、`colorSetReason`），样子与卡片四套色彩集的 ID 由 schema 枚举限制，理由不能为空。草稿已有结构化产品、类别、参数、行业、能力或认证条目时，服务端只从这些字段统计形态特征并按计数规则重算样子和理由；空草稿使用 planner 的 `styleId` 和理由，色彩始终使用 planner 的 `colorSetId` 和理由。样子和色彩集仍可自由选择；卡片上的色彩集只显示 4 套目录项，推荐 schema 不合格按现有 invalid-output 错误处理，不从标签文字猜 ID。

主题 ID → 版本化设计意图（`visualBrief`）→ 同一视觉族里的模板与区块筛选 → 受控生成。内部审美规则当前指定为 `sitecraft-frontend-less-ai-tone`，用户界面只显示样子名称。

预览示意标注为示意；只有模板和受控操作确实能落地的能力才标为可生成。没有合适素材或模板时说明缺口、给替代候选，不能假称已应用。

## 3. 内嵌的需求对齐（新建站点默认开启）

新路线复用会话存储及问题 ID/版本校验：资料 → 风格与滑杆选择 → 模型页面大纲 → 明确确认 → 后台生成。请求在需要用户选择时结束；选项提交通过结构化请求保存，不挂起 HTTP 请求。后台任务通过已有 chat API 返回持久化进度，工作台轮询读取；浏览器刷新继续观察同一个运行，不重新发模型请求。进程中断则明确显示未完成，不自动重试。

以下多题卡、样子与色彩集、operation 确认细节描述旧站点路径。

### 3.1 旧站点交互

- 新建站点（还没生成过）默认开启需求对齐；已生成站点的修改默认不走完整访谈，只在重大变化时确认。输入框上方的「需求对齐」开关可关闭，开关上写明「开」「关」，按当前会话保存，不做账户全局开关。（2026-09-24 确认，取代「建议默认关闭」）「还没生成过」指草稿历史里没有模型生成的修改。
- Agent 根据已经提供的资料，只询问会改变站点结果的缺口，不固定跑完整问卷。形态参照 harness 向用户提问：一张卡一次 1–4 题，最多 3 轮。第 1 轮通常包含主要行动、页面、样子、配色；样子排在配色前，配色按所选样子显示。还没生成过的站点即使资料已经齐全，第 1 轮也要问样子和配色；这两题由服务端按目录生成，配色选项只来自色彩集（卡上放 4 套，其余在「配色」按钮里），规划器可按资料业务形态推荐样子和色彩集并各写一句事实理由，用户选择才写入草稿。
- 每题 2–4 个稳定选项，推荐项标「推荐」并附一句理由，允许「其他，我来写」。题目分单选、多选；整张卡全部答完后一次提交，不再要求发送一段聊天文本。手机上改为底部抽屉逐题作答（上一题/下一题），只显示当前题，提交语义不变；刷新后仍按服务端答案恢复选择。
- 提供“交给 AI 推荐”或跳过非关键偏好。缺少事实/授权不能通过选“推荐”编造；允许先出带缺口提示的预览，关键发布条件仍需补齐。
- 回答后在聊天历史中显示问题与所选答案，Agent 自动继续下一步。用户不必重新发指令、不必复制问题或说“继续”。
- 关闭对齐模式只关闭完整需求访谈，保留风格入口、必要的安全/事实澄清和发布确认。关闭时已选答案保留；待回答的非必要问题取消，不继续强制追问。
- 全站生成前展示简短需求摘要和模板/方向确认；确认后生成。修改既有站点时，只确认本次重大变化，不每轮重问完整需求。

### 3.2 连续会话，不依赖一直运行的模型请求

可恢复状态建议：`collecting → awaiting_user → collecting → awaiting_confirmation → generating → editing`，另有 `cancelled` 和失败状态。对齐关闭直接走已有生成/编辑入口及必要确认。

模型每次只运行到“需要用户信息”为止：保存待回答问题后结束当前模型调用和事件流。页面保留等待中的同一任务；用户回答时以相同 `conversationId` 恢复。这满足对话连续性，不依赖浏览器标签一直开着，也不在等待期间持续计费。

对用户展示问题、选项和结果，不保存或展示模型的完整内部推理作为工作流状态。

### 3.3 最小会话与接口扩展

优先扩展现有 Chat API 和会话存储，不创建独立 alignment 服务、任务队列或第二套聊天接口。

- 会话持久化 `alignmentEnabled`、当前目标、已确认答案、一个待回答问题组及状态版本。
- 待回答问题至少有 `questionId`、`questionRevision`、选项 ID、显示文案、对应需求字段；用户只可提交当前服务端实际发出的 ID。
- 回答请求携带会话 ID、问题 ID/版本、所选 option IDs 和可选补充文本，不依赖模型从按钮标签猜用户选择。
- 复用 `clarify/status/done` 等已有事件语义；问题卡片作为结构化 clarify 载荷扩展，具体 Zod 形状在实现前与现有调用者对齐。用户等待不伪装成生成完成。
- 待回答状态保存成功后才发卡片；刷新通过受会话归属约束的读取方式取回。先实现实际工作台调用者，再定历史读取接口。
- 一张需求对齐卡可携带 1–4 个独立问题；每题使用独立 `questionId` 和选项，客户端一次提交 `selections`，服务端逐题校验后原子保存答案并继续同一会话。
- 每题选项数量为 2–4，可带 `recommended` 标记；工作台显示推荐项并允许“其他”输入，选择“其他”时必须随该题提交 note。单题卡也走同一批量提交协议。
- 规划器输出允许直接返回 `questions` 数组；服务端将首题归一化为兼容字段，不能因缺少重复的顶层单题字段而把有效问题卡判成 provider_error。规划器用顶层 `recommendation` 提供样子、色彩集推荐元数据，另外最多 2 题；服务端在草稿有结构化资料特征时用确定性样子推荐覆盖 `recommendation.styleId/styleReason`，色彩集仍按 `recommendation.colorSetId/colorSetReason` 重建；schema 不合格沿现有重试预算报告 invalid-output，不静默替换。服务端用目录重建这两题，输出长度上限要容得下这张卡。
- 规划器 invalid_output、回答被截断、超时和连接失败必须明确返回给当前请求并允许重试，不能静默替换成内置样子问题。
- Chat API 对规划失败返回 `retry_alignment` 与当前错误状态，不创建或替换待回答问题。
- 对话入口、确认方案提交和普通 SSE 在站点于请求期间消失时都返回 `site_not_found` 与“找不到这个站点”的用户文案；其它 provider/操作错误继续使用原错误目录。
- 测试夹具中已明确标记的恢复/延迟哨兵走 deterministic alignment 入口，不调用规划器；真实请求仍遵循上一条失败契约。
- 新建站点请求的模板通过初始化 operation 写入草稿的 `visualBrief`、模板和页面计划；默认站点名与公司名使用中性缺口文字，不使用演示品牌。
- 创建接口返回的草稿已经包含上述初始化 operation 结果，后续需求对齐以该模板和设计意图为上下文继续。
- 侧边栏「AI 建站」和首页的新建入口进入工作台新建地址（`/workspace?new=1`）：工作台用第一个样子作为初始化种子调用显式创建接口，再把地址换成 `?site=<新 id>`，刷新时打开同一个站；第 1 轮需求对齐卡让用户选择样子和色彩集，不把开源模板作为用户入口。`/templates` 和单个模板预览页不再是产品路由；`/api/templates/[templateId]/preview` 仍是工作台、发布页和测试使用的预览引擎。
- 资料图片（T-106、T-107）：上传走 `POST /api/sites/[siteId]/images`，每张图带用途类别（`product` / `equipment` / `facility` / `inspection`）和许可来源；同一站点上传内容相同（sha256 相同）的图片时复用已有记录、不新增，用途更新为用户这次的选择。预览桥按用途类别把图放到各自唯一的图库节点（`facility` 同时驱动首屏照片模式），按 sha256 全站去重、同一张图整页只出现一次；同 sha256 却有不同用途的旧记录不渲染，报 `images.conflict.<hash>`，不按顺序挑。无图类别隐藏图库、不留空框。产品、设备、检测的分类图库有图时，即使其文字列表为空也保留对应区块；只有检测图而没有加工能力文字时标题为「检测 / Inspection」，文字返回后恢复原标题。用户显式隐藏区块时，所属图库也隐藏。CC-BY / CC-BY-SA 图的作者、许可和来源链接统一写在页脚的图片来源说明里。
- 只有 `POST /api/sites` 明确创建站点并写盘；发布页、草稿 GET、质量矩阵、聊天/提交、图片和历史路径读取不存在的站点时返回 `site_not_found`（发布页为 404），使用 `getExistingSite`，不生成默认空草稿、不写站点文件。质量对照缺少固定站点时报告缺失并停止该次操作；commit、history、selective undo 的 store 锁定路径也只接受已存在记录，入口检查后的删除竞态不能重新创建站点。
- 重复点击/提交不能重复推进或重复 commit；过期问题、多标签页冲突、错误会话 ID 明确拒绝，并展示最新可回答状态。
- 等待和回答只修改会话资料，不直接修改站点草稿。确认后的站点变更仍走 `commitOperations`，并检查草稿 revision；换模板/已修改草稿会使旧确认失效。
- 如果已 commit 但流中断，恢复时先读取真实 revision/结果，不再执行同一份生成操作。

### 3.4 工作台布局与主题（2026-09-24 确认）

- 布局：预览居中，对话停靠右侧；样子盘和色板不再占左栏，改为对话里的提问卡片和输入框上方的「样子」「配色」按钮。平板上对话为抽屉；手机上「对话 / 预览」切换，需求对齐用底部抽屉逐题作答；375 宽预览工具栏的操作按钮都保持在视口内。375 / 768 / 1440 都要成立。
- 主题：工作台有深、浅两套，默认跟随系统；另可从 6 套色彩集里选工作台强调色。这是用户的界面偏好，与正在编辑的站点配色独立，不跟随站点变色。
- 顶栏横跨全宽：返回、站名、保存状态｜预览宽度、中/EN｜撤销、重做、发布、删除。输入框上方一排操作，分三组：需求对齐开关｜样子、配色｜公司资料、上传产品图、商品表格（次要样式），按钮都常显、高度桌面 ≥ 36px、手机 ≥ 44px；需求对齐不藏在「+」菜单里。不放开发自测用的提示句。需求对齐卡打开或新一轮到来时，对话滚到卡片顶部。出错时只有一个错误框，下面一行「已保存的草稿没有变化，可以直接重试。」
- 进行中的工作在对话里显示当前一步和步骤列表（例如「读资料和要求，规划页面和要问你的问题」「生成修改」「校验并写入草稿」），步骤只按服务端状态前进；完成或失败后淡出，失败时留下错误说明。
- 动效只用 `transform` / `opacity`，150–300ms：需求对齐卡选中、换题、提交后收起，手机底部抽屉进出，平板对话抽屉开合，面板和对话框出现，预览刷新时页面轻微变暗再恢复（已显示过的页面不再被整块遮住）。`prefers-reduced-motion` 下全部不播。
- 深浅两套主题、6 个强调色下，工作台全部文字（对话、需求对齐卡与抽屉、样子/配色面板、历史、对话框、空状态、错误、预览工具栏）对比度 ≥ 4.5:1，由 `tests/workspace-dark-contrast.test.ts` 在 1440 / 768 / 375 量出。界面上不出现英文开发标签。
- 应用一次对话修改后，服务端在 `commitOperations` 成功得到 change set 后，用该 change set 的 `appliedTargets` 生成中文改动摘要（例如「产品介绍」「优势第 1 项标题」）；模型返回的 `summary` 完全不进入历史、改动标记、对话修改摘要或需求对齐确认卡。确认卡在尚无 change set 时只显示「将修改：」和 operation 目标的中文标签。摘要只用于工作台反馈和历史记录，不写入发布页，也不向用户暴露字段路径。改动标记只来自这次修改的 change set（服务端的 `appliedTargets`）；预览桥回报的 `appliedSlots` 是页面此刻的实际落点（包括按样子默认布局挂上的区块），只用来确认这次的落点已出现在页面上，不用来生成改动标记。会话的 AI 摘要也按终态结果生成：applied 用 change set 摘要，rejected 用持久化的纯拒绝原因，conflict/error 用明确的结果原因；工作台消息的状态标签和摘要合计只显示一层前缀：已更新、已撤销、已重做由实际落点摘要负责，拒绝由状态标签负责唯一的「未修改：」前缀，重放 rejected 结果不能再添加一层前缀；不得回写 provider 或 proposal 的模型摘要。对话修改被拒绝时只显示拒绝理由，不声称发生了改动；撤销和重做用逆/正操作实际返回的 `appliedTargets` 生成「已撤销/已重做」摘要。
- 卡片和产品的可编辑目标必须稳定：`features/services/faq` 等卡片用草稿卡片 `id` 寻址，id 只允许字母、数字、下划线和连字符，最长 80 个字符；预览槽位和 `selectedTarget` 使用 `<section>.items.<id>.<title|body>`，`selectedTarget` 的传输上限为 200。`update_card` / `remove_card` 通过 `itemId`，`add_card` 的 `index` 只表示插入位置。产品草稿带稳定 `id`，预览槽位和 `update_product`、`set_product_specs`、产品图片 operation 通过 `productId`；`sku` 是可修改的型号资料，不是寻址键。旧草稿读入、API 写入和 `replace_draft` 后确定性补产品 id；已有安全显式 id 保持不变，重复显式 id、含点号等不安全旧 id 或无法唯一解析的旧 SKU 属于不支持的旧数据形态，会抛带站点、字段和旧值的 `SiteMigrationError` 让请求失败并保留原记录，预览桥缺 id 只报 missing，不能保留按序号或 SKU 的第二条寻址路径；2026-10-02 扫描本机 4814 条记录均为 0 条命中。
- 旧记录迁移：文件记录读入时，旧 history/future 的卡片 index、产品 SKU 以及对应 inverse/appliedTargets 按当时草稿状态一次性改成稳定 id，v1/v2 都升级到 `historySchemaVersion: 3` 后持久化；之后 undo/redo 只运行稳定 id operation。迁移失败抛 `SiteMigrationError`，不自动改写或回退到默认草稿。主控 2026-10-07 决定（T-131）：不继续修复各条旧记录的历史目标；列表保留失败条目，原名称、原更新时间加「旧记录无法打开」和具体原因，其他站点正常列出。工作台草稿 GET 返回 422 / `site_migration_failed`，界面显示与列表相同的原因，不显示默认内容或预览。文件与 PostgreSQL 列表均只在单条记录的迁移错误边界转成失败条目，其他存储异常继续上报。
- **批注契约与存储**：批注是站点记录之外的独立线程，保存 `pageId/pagePath`、`templateId`、`locale`、捕获时草稿 `revision`、视口/滚动位置、有限文字快照和 `capturedAt`。单目标锚点只接受稳定 `data-sitecraft-slot`（其中的卡片 `itemId`、产品 `productId` 是业务身份）；圈选记录多个 slot，只有用户明确指定 `primarySlot` 后才可交给模型修改。当前指向只报告 `attached`、`stale`、`ambiguous`，不能按文字、元素顺序、SKU 或通用 selector 猜写；快照是不可信上下文，截图仅用户主动保存。批注状态为 `open` / `resolved`，回复和标记处理不改草稿 revision；FS 使用 `.sitecraft-data/annotations/<siteId>.json` 原子写，Postgres 使用独立 JSONB 表。删除只由明确的 DELETE 操作触发。
- **批注事务与选择性撤销**：change set 可带 `annotationId`，单字段 operation 为每个实际 `appliedTarget` 保存修改后的 postcondition。按事务撤销时在 store 锁/事务边界读取当前草稿，逐 guard 核对 postcondition；仍匹配的 guard 生成 inverse operation，再以新的 manual change set 走 `commitOperations`，后来修改过的 target 不动并返回 `conflictTargets`。没有 guard 的旧历史和整组替换 operation（`replace_cards`、`replace_products`、`replace_commercial_terms`、`replace_draft`）明确拒绝选择性撤销；普通顶端 undo/redo 契约不变。
- **预览批注运行时**：工作台 iframe 与桥接消息使用固定 `typeVersion` 和每帧 `sessionId`；iframe 重载后由 frame 重新发送内容与批注模式。批注模式只允许命中声明的 `data-sitecraft-slot`，产品卡同时带 `data-sitecraft-product-id`，拖框返回完整槽位集合；桥接按唯一槽位报告 `attached` / `stale` / `ambiguous`，没有 `primarySlot` 的圈选和非 attached 批注在模型调用与 `commitOperations` 前拒绝。工作台在桌面侧栏、平板窄侧栏和手机底部抽屉显示批注状态，所有批注修改仍经过白名单 operation 和选择性撤销。
- 对话修改没有改动草稿时：系统拒绝了模型要的修改（例如资料不够的布局、用户没要求的换样子），回复只有原因「未修改：……」（去重，用「；」连接）；模型本来就没有可应用的修改时，才显示「模型没有生成可应用的内容差异，草稿和模板均未修改。」和它的摘要。
- 刷新后恢复需求对齐时，如果上一次生成或保存失败，对话里先说出原因，和当时的提示一样（例如「这次生成被截断，没有改动草稿。 可以直接重试；已保存的问题和答案仍可继续。」），问题卡还在就可以直接重新提交。只显示错误目录里的说法，其他记录显示「需求对齐没有完成，草稿没有修改。请读取当前状态后重试。」。
- 原型：[SiteCraft 工作台改版原型](https://claude.ai/artifact/BG2wuABfaVQTLPRaBWzUct)。负责人选定：方向 B 的布局与手机逐题抽屉，深浅两套主题；原型不是像素规格，实现以本节为准。

## 4. 站点代码、Skill 和提交契约

局部修正不得改变范围外 DOM 或同一文本节点的未选字符；`tests/t138-dom-scope.test.ts` 与 `tests/t138-repair-fragments.test.ts` 通过真实提交及区间反例机械检查该失败类，随 `npm test` 自动执行。

### 新路线（T-127 / T-128 / T-129）

- 模型直接输出 `header`、`footer`、`css` 和 `pages`，每页包含 ID、标题、HTML 片段。版式与文案由模型按资料和风格决定，不受区块/operation 白名单限制。公共页头页脚与一份 CSS 在各页共享。
- 生成、对话修改与恢复只通过 `commitSiteCode`：在不执行脚本的文档中解析候选并清理脚本、事件、外部资源与未授权图片 → 链接检查 → Chrome 的 375/768/1440 溢出、重叠、全文对比度和正文行长扫描，并收集 CSS 生成文字 → 合并 HTML 与 CSS 文字做数字检查和一次事实校对 → 写完整版本。正文行长仅作为质量反馈记录在检查结果的 `viewports.longLines`，不阻止存版、不触发修正轮；其他底线与清理发现的问题仍会阻止存版，并反馈给模型。最多两轮修正（初稿加两份修正版），仍不过如实显示失败，当前版本不变。失败候选与各轮结果保留在运行记录中。
- 底线拒因的修正只发送资料、拒因与对应 DOM 节点内容，不发送完整站点或历史版本。事实拒因按文本节点内的句子、辅助属性或数字定位；布局拒因发送相关页的叶子元素与公共 style 元素，避免重复发送祖先整段内容。模型用节点编号返回替换内容，系统核对编号、唯一性、原节点和重叠：text 按文本节点分组，每组以原始偏移倒序写入纯文字，提案跨节点交错不能影响顺序；同节点区间重叠直接拒绝，相邻区间允许。范围核验分别保留原文与修正后的未选字符区间（前缀、间隙、后缀），逐段核对完整内容，同时核对新长度及选中区间的写入结果，不跳过整个文本节点；title 同样按纯文字处理。文字由 DOM 转义；element/style 必须是原层级的一个完整元素，标签和 CSS 闭合，不允许浏览器自动修复缺失的结束标签。节点修改后先断言片段之外的 DOM（节点类型、文本、属性、命名空间与注释）一致，再从完整候选重新解析每页，对照独立以 DOM 节点构建的预期文档；不一致立即拒绝，完整模型回复与拒因保存在 `run.repairFailure`，不自动重发、不存版。通过后继续走 `commitSiteCode` 的清理和全部底线检查。拒因全部属于提交入口已完成的清理、没有剩余节点时，允许模型返回空替换，完整候选仍须重走全部检查。其他定位不到、节点无效或检查仍不过明确失败，不调用整站重写作为后备路径。公共页头与页脚在事实校对输入中各出现一次，各页的标题、正文和辅助文案分别完整保留，CSS 生成文字仍在检查范围内。
- 会话失败说明与拒因存档分开（T-136）：三次候选均拒收后，工作台显示简短中文说明及重试方向；完整拒因仍在 `CodeRun.issues` 与每个 `attempts[].checks.issues` 中，界面可展开最后一轮检查问题。共享 `applyCommittedResult` 将摘要限制在既有 400 字上限，并用同一合法摘要记录 lastResult/history；文件和 PostgreSQL 更新都在持久化前验证快照，非法写入不替换旧记录。读取已有会话时，仅全部校验错误都是超长字符串的情况返回 `conversationError` 和可读的 codeSite（资料、运行、版本），alignment 为 null，turns 暂不读取，界面明确提示并停用对话；不重置、不截短或改写旧文件，其他损坏继续上报。`action:state` 先识别会话警告，避免为坏会话修改任务元数据；预览和版本历史继续使用原入口。
- CSS 生成文字以浏览器渲染后的计算样式为准：读取每个 `display:list-item` 元素的 `listStyleType`，以及每个元素的 `::before`、`::after`、`::marker` 的 `content`，将解析出的字符串并入事实检查。变量、shorthand 与嵌套由浏览器解析，不再按声明文本分类或追踪变量。decimal、disc、罗马序号等标准结构序号放行；无资料来源的生成文字与 HTML 文案同样拒绝。嵌套 CSS 递归清理并保留规则与声明顺序，无法处理的规则明确拒绝，不静默改写页面。
- HTML 手写数字与正文、辅助文案属性执行同一来源检查，删除按 DOM 序列、段落或单位推断序号的豁免。核心规范要求步骤和列表使用原生 `ol` 编号或 CSS 标准计数器（decimal 等），不手写 01/02；它们沿用既有标准结构序号规则。真实手写步骤、名工程师/条自动产线/kW/L/min 数量绕过、原生列表与 counter 的成对回归在 `tests/t133-floor-checks.test.ts`。资料没有的电话、地址等可写「待补充」，占位本身不当新事实；同句中的数值、条件、范围、对象和承诺仍检查。报价、付款、交期及响应、售后及质保、认证及文件提供、合作及排产或交付等政策必须有资料对应原句，允许等价改写，没有来源则拒收，不能用行业常识或不同产品的参数差异补造政策。
- 检查器实际渲染 HTML；同元素与跨元素文字使用同一字体 em 度量，标题语义从最近的标题祖先识别，对比度按实际填充色计算，透明填充和背景裁切文字明确拒绝。正文文本按最近的块级或独立排版容器分别测量，包含 inline-block、inline-flex、inline-grid 及 flex/grid 子项；用 `Range.getClientRects()` 取各容器内文字行的宽度和字数，不把纵坐标相同的并排卡片合成一行。p、div、li、dd、figcaption、blockquote 均按此规则检查；标题、导航、参数表、按钮/控件、邮箱/电话、声明为型号/参数的字段、系统图片署名与许可信息明确列为语义豁免，普通正文和图片说明不会因换标签而漏测。这两类回归由 `tests/t128-code-boundary.test.ts` 的并排卡片／长单段正文及计算样式文字／decimal 成对用例守住。
- 图片使用已上传的 `data-image-id` 编号，系统解析本站地址，按使用记录汇总署名。系统提供询盘占位部件和登记的 Lucide 图标，模型只用 `data-system-icon` 摆放和配样式，不生成 SVG。`lib/code-site-icons.ts` 为提交白名单与静态渲染的共同登记表，由 `node scripts/generate-code-site-icons.mjs` 从现有 Lucide 组件导出，访客页无需 React 运行时；随生成 HTML 保留 ISC 许可说明。无授权图片时生成无图版。
- 页面大纲遵循用户点名页面优先、其次按业务规划、无法确定才首页/产品/联系。当前最多 12 页，超出能力必须说明；写作结果缺少已确认页面时拒绝，不能默默缩为首页。
- 每次生成或修改运行时读取 `skills/site-code-core/SKILL.md`、通用去 AI 味规范及已选风格 skill；核心规范吸收本项目叠加层的事实、文案、层级与成品规则，旧路线的禁止 CSS/operation 限制不进入新提示。
- 事实来源包括原始资料和有效版本链中用户明确提供的补充；字段更新采用最新声明，设计要求不作为企业事实。模型生成的文案不进入资料链。撤销同时恢复该版本对应的用户补充链，后续修改不重新采用已撤销的信息。
- 新路线记录在 `.sitecraft-data/code-sites/<siteId>.json`，当前验收开发机文件存储。版本快照包含作者、一句话摘要、触发请求、完整代码、检查结果及时间；除可编辑的名称外均不可变。撤销与指定版本恢复携带客户端所见 `baseRevision`，同一提交入口拒绝过期版本并返回 409；通过后重新检查目标版本并存为新版本，保留所有旧版本，刷新读取当前版本。用户在既有删除流程输入站点编号确认后，一并删除代码版本、资料与运行记录；删除与提交共用站点锁。当前没有重做、批注、快捷修改、英文版或自动删除。
- 版本历史直接读取工作台状态中的完整版本；左侧按 1 分钟、10 分钟、1 小时或本地日期分组，最新版本在前，每条显示版本号、时间、作者、摘要、检查状态、名称和当前版本标记。分钟、10 分钟与小时桶按当前本地时间实例减去桶内经过的时间，保留不同 UTC 偏移；纽约夏令时回拨后的两次 01:55 不合并，分组标题显示偏移。本地日期仍合并为同一天。右侧用已有 `code-preview` 沙盒显示选中版本各页，可切 1440/768/375。名称通过 `PATCH /api/sites/<siteId>/versions/<versionId>` 保存，最多 80 字，空串清除；只修改元数据，不改代码、检查记录或当前修订号。指定恢复使用已有 `history/restore` 入口。
- 对话修改先把用户请求、当前版本编号及版本目录（编号、名称、摘要、时间、作者，不含代码）交给模型。模型在结构化 `referenceRevisions` 数组中声明参考编号，普通修改可为空；系统不从消息做正则解析或型号判断。字段结构或编号形态非法时显示简短中文提示，不把 Zod 英文细节交给用户；任何编号不存在都会结束当前后台任务，在进度与对话中说明原因。两类失败均不调用写作、不保存版本。合法版本 ID 保存在运行记录中，完整旧代码作为不可信数据交给首次写作；同时携带当前代码，要求只取回用户指定部分并保留其余部分，事实仍以当前有效资料为准。底线拒收后的最多两轮局部修正只拿拒因对应片段与当前有效资料，不再发送历史整站。结果经 `commitSiteCode` 检查后存为新版本。区域验收按用户是否点名页面区分：点名时仅该页指定区域可变；未点名页面的“产品区”可包含各页产品区及首页产品入口，页头页脚、其他区块、联系页等范围外始终保持。范围外整段规范化 outerHTML 包含 href 与所有属性，自动生成的预览版本参数单独归一化；范围外每个可交互元素滚入视口后，核对 `checkVisibility({checkOpacity:true,checkVisibilityCSS:true})`、布局矩形宽高非零、中心 `elementFromPoint` 命中自身或后代三项结果在前后版本一致，观察后恢复滚动位置；不能只比自身样式或文字证明功能保留。`tests/t129-version-history-check.test.ts` 经真实 CLI 与 Chrome 检查祖先隐藏导航/询盘、错误链接和禁用询盘指针的负例，由 `npm test` 自动包含。存版与底线检查通过不替代该范围核对；真实模型能力不以受控 HTTP 测试代替。

- **区块库**放在 `lib/blocks/`：每个区块变体是一段开发侧 HTML（根节点 `data-sc-block="<区块>" data-sc-variant="<变体>"`，可改样式的部位标 `data-sc-part`），HTML 和 CSS 在 `lib/blocks/fragments/`（只在服务端用），配一份数据清单（`lib/blocks/catalog.ts`）：区块、变体、读哪些草稿字段、槽位（沿用 adapter 的 `selector → target` 写法）、预览桥自己渲染的固定节点、部件名、最少资料条件（例如「参数对比」要 2–4 个产品共有 ≥3 项参数）。清单是可审查数据，不存可执行 JS；区块库样子的 adapter 由清单生成（`lib/blocks/adapter.ts`）。结构可参考 HyperUI、Meraki UI（MIT，改写成自己的类名并保留许可声明）；它们的图片、图标不用，Preline 不用；第一版不用图标。

  - 常见问题、合作方式、优势在页面上的条数固定、按序号写入。页面先显示有标题或正文的条目（按草稿顺序），再轮到空条目：新草稿自带空条目，模型用 add_card 加的条目排在它们后面，按序号写入时页面只显示空条目、真的问答到不了页面。每个位置写入的是那一条自己的序号（例如 `faq.items.6.title.zh`），在工作台点它、确认修改都落在那一条上；放不下的条目改了之后，工作台提示「当前样子没有位置显示：常见问题第10项标题」这类说明。
- **站点样式**（负责人 2026-09-29 选 T-051 的做法 A；2026-09-30 决定只按用户要求使用）：模型输出结构化规则，不写 CSS 文本：`{ block, part?, media?, declarations: { 属性: 值 } }`。新 operation `set_site_style` 整份替换规则表，inverse 恢复前一份。整站生成和需求对齐不输出 `set_site_style`，也不计算或提供建议方向；用户在后续对话里明确提出外观或版式要求时，提示才展示工程工业的规格为主、目录为主、工厂实力方向菜单，并允许选择一个方向配方或追加规则。校验按 [T-051 调研](../research/区块素材与CSS校验调研-2026-09-29.md) §3.3 的白名单：区块/部件只能是清单里有的；`media` 只能是项目断点；属性按组放行；值里禁一切字符串、反斜杠、非 ASCII、`url()` 等资源函数、`!important`；`content`、`position`（除 static/relative）、`z-index`、`overflow*`、`opacity`、`transform`、`list-style*` 等整条禁用；序列化后 ≤ 8 KB、≤ 40 条规则、≤ 200 条声明。追加规则是整份 operation 的一部分。页面 CSS 由 SiteCraft 自己的序列化函数从规则表生成，加 `[data-sc-block=…]` 前缀，不透传模型原文；区块库 CSS 放进 `@layer sc-blocks`，站点样式放进其后声明的 `@layer site-style`，保证样式可以覆盖区块库，同时不能触及缺口和显隐保护。提交检查在中文三档及有英文页时的英文三档运行；只拒绝样式带来的新增溢出、重叠、槽位不可见或对比度不足，撤销/重做不重查。
- **三档检查**：`set_site_style` 提交前，在常驻的无头 Chrome 里（沿用 `scripts/check-published.mjs` 的原生 CDP 做法，不加浏览器依赖）按 375 / 768 / 1440 各渲染一次候选草稿，和不带新样式的基线比：新增横向溢出（`scrollWidth` 和元素右边界两种都查）、新增文字框重叠、槽位文字被藏，任何一项出现就拒绝这次修改，并告诉用户哪一档、哪个区块出了问题。候选草稿在内存里渲染，不先写修订再撤回。检查起不来（没有 Chrome）时报错，不跳过。

模板元数据只保留有消费者的字段：来源版本/代码许可/独立素材授权，行业与页面类型、语言、素材要求、主题倾向、支持的内容槽位及限制、已验证状态。先排除不兼容来源，再比较风格。

### 旧站点运行时归属

- `visualBrief`：用户选定的受众、主要行动、语言与设计意图；同一份数据服务模板匹配和生成。
- 模板能力说明/slot map：可编辑内容到真实页面元素的映射，覆盖和不支持项必须真实报告。声明槽位是落点工具，不是「未声明就原样留下」的成品许可。
- 素材计划：引用已有素材 ID、来源、许可、裁切/比例和事实属性，不能另建未经授权的素材镜像。开源 HTML/CSS/token 作为素材准入时，图片、字体、图标仍须单独核验。
- 白名单 operations：把被支持的文字、图片、主题变化转成可撤销修改。未确认的设计预案先存会话，持久化到站点时也不能绕过 commit。
- 双语文案使用一条 operation 携带 `{zh, en}`；英文缺口写 `To be provided`。草稿的 `englishReady` 由实际写入非缺口英文的 operation 设置，发布页按该数据标记决定是否提供 EN，不通过与默认句子比较推断。
- 商品类别属于双语文案，随商品 operation 携带 `{zh,en}`，发布页和工作台按当前语言读取；旧单语类别只作为旧草稿兼容读法。行业同样是双语字段。公司名和站名只保存资料里的原文（模型给出的译名不采用），资料没有时保留中性名称。认证状态按页面语言显示（已有 / Certified、认证中 / In progress）。
- 所有会写入双语英文的 operation（包括卡片更新）都必须把 `englishReady` 的前值纳入 inverse，撤销后恢复英文开关状态。
- 模块选择：只在同一 `visualBrief` / 模板族内决定使用哪些已准入区块。跨模板或跨站 HTML 拼接不是合法 operation。
- 目录类内容：产品可带规格参数表；站点可有应用行业、加工能力、认证状态三个目录区块，均通过 operation 写入。认证状态分为已有、认证中、待补充；访客页只显示已有和认证中，全部待补充时整块隐藏。产品图片带署名信息，CC-BY 类许可在访客页署名。
- 询盘入口：询盘表单是站点的主要行动，不属于资料事实，不受缺口规则影响；资料没写询盘文案时用界面文字作标题。
- 新草稿不含演示文案：公司事实字段是「待补充 / To be provided」，标题是中性界面文字；说明类字段（区块引言、询盘正文、首屏副标题、关于正文）整段是缺口时整句不显示。新草稿也不带商品；访客页上商品区既没有可显示的商品也没有产品类别照片时整块隐藏，指向它的导航和按钮一起隐藏，工作台预览里保留「产品资料待补充」提示。
- 没有草稿的页面（模板页缩略图、模板预览页）：工程工业页面按同一缺口规则显示，没有内容的问答、步骤和联系行不显示，整块都空的区块连同指向它的导航和按钮一起隐藏，页脚的产品一栏也不显示，只剩页头、首屏的询盘按钮、询盘表单和页脚。有草稿时（包括工作台预览）按上面的规则。

不为了文档名称同时持久化 DESIGN.md、page-plan.json 和 visualBrief 三套重复数据；先明确具体消费者再选字段。

### 旧站点 Skill 使用

- 提问不改稿、非法目标不误写、回答后恢复且只提交一次。
- 用同一公司资料换风格，验证真实布局/字阶/图片处理或受控主题变化；仅主题名称/摘要变了不算有效。
- 使用资料驱动检查 + 人工核对关键数字、认证、评价、案例；不承诺仅用关键词规则证明所有语义事实。
- 浏览器在 375/768/1440 CSS 像素及拥挤断点检查，覆盖菜单、焦点、表单错误和结果；表单成功提示不是收件证据。
- 浏览器测试统一使用 `SITECRAFT_BASE`（缺省 `http://127.0.0.1:3034`）。开发环境的 `/api/health` 响应额外带 `testIdentity.cwd`，测试启动时把它和当前工作区路径核对；路径不一致或服务没有开发标识就直接失败，避免 worktree 测到另一份代码。`NODE_ENV=production` 时不返回该字段，因此生产路径不暴露测试标识。

- 浏览器助手不复用已有 CDP 端点，也不接受显式调试端口覆盖；Chrome 使用自选端口，端口只从本次 user-data-dir 的 `DevToolsActivePort` 读取，避免 worktree 之间按 PID 推导端口发生碰撞。

- 盲评界面隐藏流程组、核验记号、默认对照和冻结版本等内部标记；质量基线的冻结 HEAD 由服务端运行时读取，不在界面写死。
- 不机械禁止常用色彩/卡片/字体；记录重复营销措辞和缺少企业特征等具体问题。

## 6. 数据与执行边界

DeepSeek 为当前提供方，请求模型名为 `deepseek-flash`（对话与视觉同一条）；质量优先；保留有限超时、用户取消和失败说明。外发资料最小化，密钥只在服务器环境变量内，不送入 prompt、日志或浏览器。

新路线模型调用使用既有 DeepSeek 配置。写页固定thinking enabled；事实校对默认enabled，显式诊断可设 `SITE_CODE_FACTS_THINKING=disabled`；局部修正默认disabled，可设 `SITE_CODE_REPAIR_THINKING=enabled`。两种用途开关均只接受enabled/disabled；共用内容开关已删除。独立盲评两站均偏好思考写页，非思考facts对T-133报价候选六次均漏拦，故write/facts保留思考，只让repair默认非思考（见T-138）。规划保持enabled与既有strict函数输出，版本参考选择保持现状。非法用途值在该调用付费前拒绝，不静默回退。调用记录保存实际请求的 `thinking` 值，健康接口 `deepseek.codeContentThinking` 返回write/facts/repair的非敏感模式映射，供评估预检。页面大纲、站点代码、局部修正和事实校对预算均为 65536，每次最多 300 秒。规划通过 DeepSeek `/beta/chat/completions` 的 strict 函数 schema 提交，只接受一次 `submit_page_plan` 的参数，不用普通正文替代；其余调用仍用 JSON 输出。上游 schema 不能代替本地字段、长度、首页、重复页面与用户风格校验；本地大纲校验失败显示简短中文。调用记录保存实际卡片顺序、结束原因与回答长度等诊断元数据，不保存原始推理或 prompt；执行者规划诊断的原始响应只放 gitignore 的私有 artifacts。HTTP 失败、截断、超时和格式错误立即报告，不自动重试；底线拒绝后的最多两轮修正是明确的内容修改，检查证据保留。

每个后台运行记录规划、写页、局部修正、事实校对的调用目的、模型、HTTP 状态、耗时和上游返回的 prompt/completion/total token 数。上游提供 `completion_tokens_details.reasoning_tokens` 时记录输出中的推理用量子集；没有就记为未知，不从文字反推，不重复计费。无 usage 的响应明确记为未知；不保存请求、密钥或模型思考文字。运行上下文彼此隔离，提交入口结束后再持久化调用记录，不在提交锁内另取站点锁。

旧路线 `deepseek-flash` 默认开思考模式，推理 token 计入 `max_tokens`（实测一个 8192 的回答全是推理、没有内容）。为保住质量，思考模式保持默认，预算按实测放宽：整站生成（结构化修改）至少 65536、每次最多等 300 秒（实测不设上限时 13.7K–22.7K，其中推理 11.2K–18.7K，57–95 秒；上限 32768 时注塑仍有一次用到 32761、其中推理 31191，被截断；现阶段成功率优先，不设成本和等待时长指标）；需求对齐规划 65536、300 秒（T-110 的短路径注塑规划输入仅 3757 tokens，8192 输出预算全被推理耗尽，未产生 JSON；T-122 与整站生成使用相同余量）；看图和预览审查仍是 800（看图实测 435–495）、每次 45 秒。回答不是 JSON、格式不对或服务端 5xx/429 时仍再试一次，但两次合计有上限：整站生成与需求对齐规划均为 360 秒，第二次只用剩下的时间，一点不剩就不再发请求，告诉用户第一次的失败原因。四个调用（需求对齐规划、整站生成、看图、预览审查）的回答达到上限时都不再重试，直接告诉用户「这次生成被截断，没有改动草稿。」（错误码 `truncated`，看图和预览审查的接口也用错误目录的这句），规划这一步说「需求对齐规划被截断，原需求没有修改草稿，可以重试。」。
