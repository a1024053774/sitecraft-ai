# 生成过程可感知与真实流式预览

- 日期：2026-09-02
- 场景：后台已有 SSE 和板块级进度，但生成页长期停留在静态框图，用户无法确认网站是否真的在生成
- 方向：产品体验 / 流式架构
- 置信度：8
- 层级：复合
- 状态：部分落地（固定阈值待真实 provider 校准）
- 复用量：2
- 来源：[NN/g Progress Indicators](https://www.nngroup.com/articles/progress-indicators/)、[MDN Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)、[Vercel AI SDK Streaming Custom Data](https://ai-sdk.dev/docs/ai-sdk-ui/streaming-data)

## 问题

当前生成页显示抽象框图、板块标签和一行进行中文案。即使后台正在通过 SSE 工作，只要框图不随真实产物变化、当前任务长时间不更新，用户看到的仍是“静态等待页”。这会把模型延迟放大成“产品卡死”，也无法让用户判断已经完成了什么、失败后能否保留已有结果。

## 借鉴方案

把生成反馈拆成两个同步通道：任务通道解释“现在在做什么”，产物通道直接展示“网站已经长成什么样”。任务通道只显示服务端真实事件；产物通道优先生成首屏，并在每个可用板块完成时把真实内容补进同一个预览，而不是持续播放与产物无关的骨架动画。

建议的体验节奏：请求提交后 1 秒内确认需求；模板匹配完成立即显示真实模板结构；首屏完成后马上替换首屏占位并允许预览；其余板块继续后台生成，每完成一个就局部高亮更新。超过一个可感知时间窗口仍无业务事件时，用 heartbeat 明确说明当前子任务和已等待时间，但不伪造百分比。

## 关键决策

- 保留现有 SSE，不另建 WebSocket；MDN 将 SSE 定义为服务端到客户端的单向事件连接，符合生成任务的主要数据流向。
- 事件契约区分 `phase_started`、`section_started`、`content_delta` 或 `section_ready`、`preview_patch`、`heartbeat`、`retrying`、`done`、`error`，前端不从定时器猜进度。
- 首屏优先。导航和 hero 可用后立刻渲染真实预览，其余板块继续生成；最终校验仍可保留一次原子提交，避免草稿数据半更新。
- 抽象框图只用于最初几秒。第一份真实内容到达后，必须切换为 `SiteRenderer` 的局部结果；刚更新的区域短暂描边或淡入，帮助用户感知变化。
- 板块标签使用真实状态：等待、生成中、已完成、重试、失败。失败板块不抹掉已完成板块，允许保留部分草稿并继续进入编辑器。
- 对长空窗发送 heartbeat，并带当前子任务、已耗时和重试状态。heartbeat 只能解释等待，不能冒充生成进度。
- 支持断线重连和任务恢复：以 `jobId`、事件序号和已完成板块为恢复边界，避免刷新页面后从零开始。

## 建议指标

- 首次状态反馈 TTFA：目标小于 1 秒。
- 首次真实预览 TTFP：目标小于 5 秒，至少先出现模板结构或首屏真实文案。
- 业务事件空窗：P95 小于 3 秒；超过阈值必须出现真实 heartbeat。
- 同时观察生成页退出率、重复点击率、重试率、首屏出现后的继续等待率，以及“进入编辑器”转化率。

## 2026-09-02 产品约束补充

- 目标用户：企业老板、外贸业务员等希望通过自然语言完成建站的非技术用户。
- 当前性能基线：正常建站约 30 秒；异常时没有终态，会无限停留在生成页面。
- 回归范围：用户确认无限卡死是在当天修改后出现，暂时无法定位到具体模板或板块。
- 部分成功策略：先创建可用网站，明确提示未完成板块并允许后续补全。
- 模板降级策略：允许系统推荐并自动切换到兼容模板，但界面必须说明发生了切换及原因。
- 优先级：成功率与速度高于最少模型调用次数。

由此得到的待验证时间预算：正常路径保持 30 秒目标；业务事件长时间无变化时进入恢复流程；全局截止时间到达后必须交付部分成功结果或明确失败，禁止无限等待。具体阈值需结合一次真实 SSE 时间线和模型延迟分布确定，不能仅凭主观设置。

## 2026-09-02 落地验证与可复用规则

本轮按“搜 → 筛 → 炼 → 验 → 沉淀”复用了 NN/g 的真实进度反馈、MDN 的 SSE 单向事件模型、Vercel AI SDK 的结构化流式数据，以及项目既有模板快照经验。筛选时只保留能映射到当前 Next.js + SSE + 结构化草稿架构的做法；最终以下规则已由本地确定性测试、生产构建和浏览器 E2E 验证。

### 生成编排

- **有限 deadline 统一覆盖整条链路**：客户端用同一个 `AbortController` 覆盖创建站点、读取 revision 和消费 SSE；45 秒只作为慢请求告警与恢复检查点，更晚硬截止才取消底层请求并进入可重试终态。计时在服务端终态停止，不能继续增长。
- **取消必须传播到底层 provider**：服务端 25 秒主截止触发 `AbortSignal`，模型请求、批次和恢复任务共同消费该信号，不能只让 UI 停止等待而留下后台悬挂请求。
- **`done` 到达即终态**：完整、部分交付、模板降级、冲突和错误都由结构化终态收口。完整成功可短延时进入工作台；部分交付和模板降级停留展示结果并提供明确的继续按钮。
- **恢复预算独立且并发隔离**：正常批次保持一次调用；整批异常才按板块并发恢复，每板块最多 8 秒，自评最多 6 秒且 fail-open。某个板块挂死不能阻塞兄弟板块或最终提交。
- **进度来自真实状态**：显示进度由等待、生成、恢复、完成、失败及服务端终态计算，时间只能辅助封顶，不能伪造完成百分比。

### 能力协商与初稿预览

- FAQ 无独立槽位时自动映射到联系板块的折叠内容，并确保联系板块存在；这属于兼容适配，不应作为拒绝建站的错误。
- 三个推荐候选以业务描述的稳定种子轮换，同一输入可复现，不同业务不会永久展示同一组合；主推荐仍保持第一位。
- “模板原貌”与“已填内容预览”分开：已填草稿通过同源、10 分钟有效、完整 schema 校验的短期快照跨标签传递，模板 ID 不匹配或过期立即丢弃。

### 静态模板

- Next 静态导出不能只验证 HTML 200；必须验证浏览器实际应用 CSS、JS runtime、图片、字体和计算样式。
- Next 模板在 `dist/_next` 存在时从静态根读取；只有旧式 `.next/server/app` 入口才回退源码 `.next`。路径解析始终保持根目录边界检查。
- SHADCN PRO 在构建阶段写入站内 `assetPrefix`，使 HTML、RSC 和 webpack runtime 使用同一模板资产 API；初始属性重写不能替代 runtime 公共路径。构建期 Google Fonts 改为本地系统字体栈，避免网络失败破坏快照生成。
- wrapper 的 iframe 高度依赖整条父级链；预览画布直属 wrapper 必须有确定的 `height: 100%`，不能只给 iframe 自身设置高度。

### 工作台冲突接管

- 确认后的破坏性请求必须与普通请求共享 HTTP 错误、绝对超时和取消语义。收到 revision 409 时采用服务端最新快照、释放输入状态并明确提示，旧操作不得覆盖新草稿。

## 2026-09-02 真实测试反证与修正

用户随后在真实建站流程中验证到：45 秒硬截止到达时仍没有可用网站。这个结果证伪的是“45 秒适合作为产品硬截止”，不是“请求必须有限、可取消并进入明确终态”这条可靠性原则。

从第一性原理看，需要把三个目标分开：活性保证负责消灭无限卡死；交付成功率要求不能过早杀死仍可能完成的任务；速度目标要求继续缩短真实 provider 的关键路径。用一个 45 秒常量同时承担三者，会把“避免无限等待”错误地实现成“提前终止慢但可成功的建站”。

后续规则修正为：45 秒触发慢请求提示、恢复检查和可选继续等待，不直接中止；更晚的硬截止负责兜底取消并保留恢复指针；最终阈值依据真实事件时间线、P50/P95、完整交付率和部分交付率校准。正常路径仍以约 30 秒为目标，不能通过单纯放宽硬截止掩盖性能问题。
