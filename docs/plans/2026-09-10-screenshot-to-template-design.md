## 二、实测经验：手工做风机模板这一小时踩到的东西

实测对象：客户提供的「风机设备企业官网」两张截图。
产物：`vendor/industry-templates/fengji/`（index.html + styles.css），已注册为运行时模板。

### 2.1 系统层缺陷（代码问题，必须先修）

| # | 问题 | 实测证据 | 严重度 |
|---|---|---|---|
| **A1** | **模板确实承载的板块被生成端隐藏** | 站内无商品 → `buildGenerationPlan` 下发 `set_section_visibility(products,false)` → 注入桥把 `[data-sitecraft-scope="products"]` 设为 `display:none`，**按截图做的 8 个产品卡一起消失**。实测 `productsDisplay:"none"`、`productsHiddenAttr:true`、页面总高仅 900px | 🔴 阻断 |
| **A2** | **AI 越界改不存在的卡** | 报 `features item 4 does not exist`——模板只有 3 张 features 卡，模型想改第 4 张。3 次生成失败 1 次（偶发） | 🟡 偶发但打断流程 |
| **A3** | **正文硬卡 40 字** | `copyLengthLimit`（`lib/site-operations.ts:629`）对 `about.body`/`hero.subtitle` 是 **40 字硬拦**（`exceedsLimit` → `return false`，是 reject 不是提示）。截图里那段企业简介 60+ 字**根本写不进去** | 🔴 阻断 |

> **A1 的归因要精确**（2026-09-10 复审修正）：
> 问题**不是**「静态区被误判成数据区」，而是**生成端在站内没有商品数据时，把 `products` 放进了 `hiddenSections`**——
> 可这个模板的 `products` 区**是有内容的**（模板自带的 8 个产品卡）。
> 生成端只知道「站内没有商品数据」，**不知道「模板自己承载了产品区」**。
>
> 所以修法有两种可能，**实施前必须先验证是哪一种**：
> - **① 生成端修**：有商品槽位声明的模板，别把它加进 `hiddenSections`；
> - **② 注入端修**：静态区（`data-sitecraft-static`）不响应 `hiddenSections` 的 `display:none`。
>
> 若照原文档的「静态区协议」直接去改注入端，**很可能修在错误的一层**。

**A1 是根子**：系统**不知道「模板自己承载了哪些内容」**——
只知道「数据里有没有」，不知道「模板上有没有」。真实工厂站大量内容是模板自带的（分类、栏目、资质），
这个盲区不补，做多少个模板都会撞同一面墙。

### 2.2 数据模型装不下的板块（结构问题）

| 截图上有 | 系统里 | 结论 |
|---|---|---|
| 8 个产品分类（环保/涂装/高温/插入式…） | ❌ 无「分类」实体；`products[].category` 只是个字符串 | 只能静态 |
| 顶栏 8 项导航 | ❌ `navigation` 固定 5 键，不可增删 | 只能静态 |
| 新闻中心 | ❌ 无对应 section | 只能静态 |
| 荣誉资质 | ❌ 无对应 section | 只能静态 |
| 长企业简介 | ❌ 40 字上限（A3） | 写不进 |
| 产品照片 / 背景照 | ❌ **无法从截图提取图片文件** | 需原图或占位 |

### 2.3 流程层：9 个问题，一条都没定

输入形态 / 谁产出 / 装不下的板块怎么办 / 怎么保质量 / 失败怎么办 / 多快 / 多少成本 / 人在哪一环 / 怎么验收。

### 2.4 场景缺口：**中途离开**（用户提出，原设计完全没覆盖）

原设计把流程想成**一条直线**（上传 → 生成 → 进工作台），默认用户会一口气做完。
但真实场景是：**用户可能在第 2 步关掉页面**（等不及、有事、网断）。

**这个场景暴露三个缺口**，详见 §4.10：

| # | 缺口 | 本质 |
|---|---|---|
| G1 | 截图没地方存 | 只存了"结果"，没存"过程材料" |
| G2 | 生成完了，用户一关页面就全丢 | 把"用户等不及"和"用户不要了"当成同一件事 |
| G3 | 找不到未完成的任务 | 没有"任务"这个实体，只有"站点" |

> **更深一层**：**"站"和"做模板这件事"被混为一谈了。**
> 站是**产品**（客户要的网站），做模板是**生产过程**（我们怎么把它做出来）。
> 现在**生产过程的痕迹没地方记**，所以断了就找不回来。

### 2.5 最根本的一条

**手工写 HTML 是「模型能力」，不是「项目能力」。**
换个会话、换个模型，结果完全不同——不可复制、不稳定、慢。
**这就是「用户上传截图到拿到模板时间太长」的根因。**

## 三、用户已定的决策（2026-09-10）

### 3.1 前置能力核实：项目的 AI **能看图**（实测，2026-09-10）

用真实截图跑项目配置的模型（`deepseek-v4-flash`）：

```
问：这张网页截图里，顶部导航栏有哪些菜单项？主标题写的是什么？
答：首页、关于我们、产品中心、新闻中心、行业应用、荣誉资质、联系我们
    主标题：某机械风机工业
prompt_tokens: 847
```

**结论**：整条路的可行前提**成立**——项目自己的 AI 就能读截图，不需要外挂能力。
**成本极低**：一张 1440×900 截图仅 **847 tokens**。

> **这条决定了优化方向**：读图便宜、**生成 HTML/CSS 贵**（一次要十几 KB 代码）。
> 所以「快」与「稳」的关键不是让模型少看图，而是**让模型少写代码**——见 §4.4 设计系统。

### 3.2 决策表

| # | 问题 | 决策 | 影响 |
|---|---|---|---|
| 1 | HTML 由谁产出 | **模型根据截图产出 HTML** | 每次结果可能不同 → 必须靠约束 + 门禁 |
| 2 | 装不下的板块怎么办 | **模板声明「静态区」** | 见 §4.5（**注意 A1 归因修正**） |
| 3 | 截图里的照片怎么办 | **三级来源**：原图 → **从截图提取** → 占位（2026-09-10 评估后升级） | 见 §4.6 |
| 4 | 谁说了算能入库 | **规则门禁自动判** | 见 §4.7 |
| 5 | **给谁用** | **客户自助上传** | **最严的一档**，见 §3.3 |
| 6 | **像到什么程度** | **大致像就行** | 版式/配色/板块顺序对即可，不苛求像素级 |
| 7 | **多张截图** | **合成一个单页** | 不依赖多页改造，本轮可做 |
| 8 | **重试仍不合格** | **降级入库 + 告知** | 入库但标 `isolated`（不被 AI 推荐），并回报原因 |
| 9 | **模板归属** | **不沉淀全局模板库**；存本站本地 | 见 §4.9 |
| 10 | **中途离开** | **当成暂停**，不是放弃 | 见 §4.10 |
| 11 | **半成品清理** | 超过 **48 小时**自动删 | 只删未完成的，`done` 的保留 |
| 12 | **生成完成后截图** | **保留**（能重做） | — |

### 3.3 决策 5（客户自助）带来的硬约束

这是四个选项里**最严的一档**，它把设计重心整个挪了：

| 维度 | 内部代建 | **客户自助（本次）** |
|---|---|---|
| 等待 | 能等 10 分钟 | **等不了 → 目标 ≤3 分钟** |
| 输入质量 | 我们会挑好截图 | **客户什么都传**：半张图、手机拍屏、带广告弹窗、甚至不是网站的图 |
| 出错 | 我们看日志 | **客户看不懂，只会觉得"坏了"** |
| 成本 | 每单可控 | **每次上传都烧 token，失败重试烧双倍** |

**派生出的设计要求**：
1. **必须有输入侧把关**——截图不合规要**当场拦下并说清为什么**，不能等生成完才发现。
   原设计完全没有这一层。
2. **必须给进度反馈**——自助用户不知道要等多久，沉默 2 分钟就会关页面。
3. **失败信息要说人话**——不能吐 `quality_gate_failed` 这种给工程师看的东西。

### 3.4 决策 6（大致像就行）的意义

这条**不是降低标准，是让自动化成为可能**。
像素级还原这个模型做不到，追求它就必须人工兜底，而那等于放弃自动化。
**"大致像" + 客户提意见再改，才是能规模化的形态。**

## 四、核心设计

### 4.1 输入

```
必填：1~N 张截图（首页 + 关键内页）→ 合成一个单页模板（决策 7）
选填：原图（产品照/背景照）—— 没有则用占位图形
选填：企业基本信息（公司名/行业/电话）—— 没有则由模型从截图读
```

#### 4.1.1 输入把关（原文档完全缺失，客户自助下必须有）

**决策 5 是"客户自助上传"**，所以输入质量不可控。必须在**花钱生成之前**拦下不适合的输入。

| 检查 | 拦什么 | 怎么判 |
|---|---|---|
| 是不是网页截图 | 传了 logo、产品照片、Word 文档截图 | 模型读图后返回 `isWebsiteLikely` + 理由 |
| 图片是否可用 | 全黑、全白、严重模糊、截断（只有半屏） | 尺寸 + 模型判定 |
| 分辨率下限 | 手机拍屏导致文字糊成一片 | 宽度 ≥ 800px 且模型能读出标题 |
| 张数 | 超过上限（建议 ≤6） | 直接拒绝并说明 |

**拦下时的输出必须是给人看的**：
```
❌ 这张图看起来不像网页截图（我识别到的是：一张产品照片）
   请提供包含导航栏和标题的网页整屏截图。
```
**不是** `invalid_input` 这种给工程师看的。

> **为什么这一层值钱**：自助场景下，一次无效生成 = 白烧 token + 客户白等 2 分钟 + 一次差体验。
> 前置拦截的成本几乎为 0（一次读图 847 tokens），收益是整个失败率的下降。

### 4.1.2 🧪 生成侧实测结论（2026-09-10，真实 API 调用）

> **这一节全部是实测数据，不是推演。** 脚本：`test-results/selfcheck/gen2.mjs`

#### 决定性发现：`reasoning_effort: "none"` 是必须的

| 指标 | 默认（开推理） | **关推理** |
|---|---|---|
| 耗时 | 62 秒 | **9.2 秒** |
| completion_tokens | **16000（打满上限，被截断）** | **2942** |
| ├ reasoning | **14465（90%）** | **0** |
| └ 实际代码 | 4286 字符（**被截断**） | **8530 字符（完整）** |
| `data-sitecraft-slot` | **0 个** | **23 个** |
| `data-sitecraft-scope` | 0 | **7** |
| `data-sitecraft-static` | 0 | **8** |
| 结尾 `</html>` | ✗ 没写完 | ✓ |

**同一个模型、同一张图、同一套提示词，只改一个参数，结果天差地别。**

**原因**：`deepseek-v4-flash` 默认长推理，**推理吃掉 90% 的 token 预算**，
导致 ①页面写不完 ②完全顾不上格式契约。
**关掉后预算全给代码**，反而既完整又守规范。

> **这条推翻了一个隐含假设**：「模型会遵守提示词里的格式要求」。
> **实测：在推理模型上，格式契约和推理开销是竞争关系**——推理赢了，契约就没了。

#### 自检循环有效且准确

把「设计稿 + 自己刚生成的渲染图」一起喂回模型：

```
耗时 3.2 秒 · 315 tokens
产出 8 条具体差异 + 严重度分级
```

**人工核对结论**：**它是对的**。其中标为 `high` 的「产品中心板块重复」——
渲染图上**确实出现了两次「产品中心」**（y≈925 与 y≈1115）。

> 这条直接对付学术论文发现的 **70-80% 图案补全偏差**：一次性生成治不好，**但生成→渲染→看一眼→改能**。

#### 成本重算（比原估算低约一个量级）

| 项 | tokens |
|---|---|
| 生成（关推理） | ~**4300** |
| 自检（两张图 + 分析） | ~**2000** |
| **一轮合计** | **≈6300** |
| 折合人民币（用户提供的 DeepSeek 空闲时段价：输入 1 元/M、输出 4 元/M） | **≈ 2 分钱** |

**原估算「5 分~2 毛」作废，实际约 2 分钱。**

### 4.1.3 抄来的参考实现（不重复造轮子）

用户要求：**能抄成熟产品就抄，节省时间和 token，然后验证能否借鉴**。

| 来源 | 抄什么 | 适用性核实 |
|---|---|---|
| **`abi/screenshot-to-code`**（73.9k★，做同一件事） | ① **自检循环指令**（生成后渲染看一眼再改）② `create/image.py` 的图片转码提示词 ③ **多截图处理策略** ④ `policies.py` 的能力开关模式 | ✅ **已实测第 ① 条有效**；③④ 可直接用 |
| 同上 | `design_system.py` —— 设计系统**只是一段 14 行的提示词块**，不是复杂机制 | ✅ 印证 T1 不必造重机制（**但 CSS 本身仍要写**） |
| 同上 | `extract_assets` —— **从截图里提取图片素材** | ⚠️ **我们做不到**，需单独评估（见 §七 风险） |
| **`AnxForever/stylekit`** | "可导出 AI Rules" 的**文件组织方式** + CLI/lint/视觉基线 | ⚠️ **部分适用**：它管的是「人改这个仓库」，**不是「约束 AI 生成的产物」**，场景不同，只借鉴组织方式 |
| **BullMQ** | 任务状态机 | ❌ **核实后判定多余**（本地单进程），见 §4.10.2 |
| 业界通用 | **按钮 pending 状态**（防重复提交） | ✅ 见 §4.11 |

> **如实说明**：大部分可抄的是**提示词与流程**，不是现成代码。
> 我们特有的（槽位契约 / 断点恢复 / 静态区）**抄不了，必须自己写**——
> 因为 abi 不做「可编辑模板」，它只产出一个 HTML 文件。

### 4.2 产出

**两种产物，位置不同**（决策 9）：

```
① 客户上传截图生成的模板（一次性，不共享）
   .sitecraft-data/generated-templates/<templateId>/
     index.html · styles.css · assets/

② 我们自己做的行业模板（公共资产，进 git）
   vendor/industry-templates/<templateId>/
     index.html · styles.css · assets/
     sitecraft.template.json     ← 只有 ② 需要登记单（① 不进全局注册表）
```

> **更正**：本节原先只写了 ②，但本设计的主线产出是 ①。
> 两者混用会导致客户模板被写进 `vendor/`（进版本控制、当公共资产），**与决策 9 直接冲突**。

### 4.3 流程

```
用户上传截图（+原图）
      ↓
模型读图 → 产出 HTML + CSS
      ↓  （按「设计系统」与「槽位规范」组装，不是自由创作）
写入前处理：槽位清点 + 补全（已有 `lib/template-slot-injection.ts`）
      ↓
规则门禁自动判（`lib/template-quality-gate.ts` 扩展）
      ↓  不过关 → 带反馈自动重试（上限 N 次）
落盘到**本站本地**（**不注册全局模板库**，见 §4.9）
      ↓
工作台预览 → 可继续用 AI 改 / 直接编辑
```

### 4.4 让模型「稳」的三样约束

这是整个设计的重心。不给约束，模型每次产出都不一样。

> **复审修正（2026-09-10）**：本节原先写成"三样约束"，读起来像**已经有了**。
> 实际核实：**三样一样都没有**——
> - **没有模板级设计系统**：`app/globals.css`（1074 行）是应用自己的界面样式，与模板无关；
>   `vendor/` 下的 22 个模板各自带**自己那套构建产物 CSS**（screwfast 43KB、awesome 20KB），互不共享。
> - **没有静态区协议**：全仓无 `data-sitecraft-static`。
> - **槽位规范是隐性的**：只在 `lib/template-runtime.ts` 的 `KNOWN_TARGETS` 里以代码形式存在，
>   没有一份"写模板时必须遵守"的成文规范可给模型看。
>
> **所以这不是"复用已有约束"，是"要建一套约束"。** 工作量要按"新建"估，不是按"接线"估。

| 约束 | 内容 | 解决什么 | 现状 |
|---|---|---|---|
| **① 设计系统** | 一套预置 CSS 变量 + 基础组件（按钮/卡片/导航/表单/栅格）。模型**引用**，不重新发明 | 风格一致、代码量小、生成快 | ❌ **需新建** |
| **② 槽位规范** | 必须打哪些 `data-sitecraft-slot`、怎么命名、集合槽怎么编号 | 生成的内容「可被 AI 填充、可被用户编辑」 | ❌ **需成文**（现仅存于代码） |
| **③ 静态区协议** | `data-sitecraft-static` 标记模板自带内容 | 解决 A1（**归因见 §2.1 修正**） | ❌ **需新建** |

> 这三样落地后，模型的工作从「设计一个网站」变成「**按规范组装一个网站**」——
> 这是「快」与「稳」的同一个解。

#### 4.4.1 为什么设计系统是**核心中的核心**

实测成本分布（§3.1）：**读图 847 tokens，而一次产出是 11KB HTML + 19KB CSS**。

**读图便宜、写代码贵。** 所以"快"与"稳"的关键不是让模型少看图，
是**让模型少写代码**——设计系统把这部分从"每次生成"变成"一次性预置"。

**与既有 `designTokens` 的关系**（`lib/site-document.ts:48`）：现有 designTokens 管的是
`primary/secondary/accent/fontStyle/radius/density` 这几项**换肤变量**，
而设计系统要提供的是**结构组件**（栅格、卡片、导航条、表单），两者是互补不是替代。

#### 4.4.2 这一项的代价（原文档缺）

设计系统本身**要先做出来**，而且要做好——它做得不好，模型产出的每个模板都会继承它的毛病。
这是**一次性的基建投入**，不是接线工作。原文档把它的成本写成了 0，是错的。

### 4.5 静态区协议（解决 A1）

**新增 `data-sitecraft-static` 属性**，标记「这块是模板自带的，不是数据驱动的」。

```html
<!-- 8 个产品分类：系统里没有分类数据，是模板固定的栏目 -->
<div class="catgrid" data-sitecraft-static="categories">
  <a href="#products">环保风机<span class="more">MORE</span></a>
  ...
</div>

<!-- 顶栏 8 项导航：navigation 只有 5 键，这里是模板固定栏目 -->
<nav class="mainnav" data-sitecraft-static="navigation">
  <a href="#top">首页</a><a href="#about">关于我们</a>...
</nav>
```

**系统要知道的三件事**：
1. **不隐藏** —— 不响应 `hiddenSections` 的 `display:none`
2. **不参与数据填充** —— 注入桥跳过它
3. **不参与覆盖统计** —— 既不判缺失，也不计入已填

#### 4.5.1 嵌套规则（原文档缺失，会直接做错）

**真实模板里，静态区和数据区是互相嵌套的。** 我的风机模板就是活例子：

```html
<section id="about" data-sitecraft-scope="about">
  <h2 data-sitecraft-slot="about.title">关于我们</h2>
  <p  data-sitecraft-slot="about.body">…</p>
  <div class="about__cards" data-sitecraft-scope="features">
    <article><h3 data-sitecraft-slot="features.items.0.title">公司简介</h3>…</article>
    …
  </div>
</section>
```

如果按"整块静态"处理 `about` 区，**那 3 张数据卡就永远填不进内容**——而它们是要被 AI 写的。

**所以协议必须定边界。规则如下：**

| 规则 | 说明 |
|---|---|
| **R1 静态区不向外传染** | `data-sitecraft-static` 只作用于**它自己那一层**，不因为祖先有它就把后代也当静态 |
| **R2 数据槽优先** | 一个静态区内部的 `data-sitecraft-slot` **仍然有效**——它照样参与填充与统计 |
| **R3 禁止静态区嵌套静态区** | 门禁判 blocker（嵌套会让"这块归谁"说不清） |
| **R4 静态区不得包住 `data-sitecraft-scope`** | 否则那个 scope 的节归属会被静态区吞掉，门禁判 blocker |

> **R2 是关键**：它把"静态区"从"一整块不动"重新定义为
> **「这一层没有槽位，所以系统别来管它；但它下面的槽位照样算数」**。
> 这样 8 个分类格（静态）和 3 张图标卡（数据）才能共存在同一个区块里。

#### 4.5.2 A1 的修法取决于归因

**如 §2.1 所记**，A1 是「生成端把有内容的板块加进了 `hiddenSections`」，**不是**「静态区被误判」。
所以实施顺序是：

1. **先验证归因**：确认 `buildGenerationPlan` 是否给有 products 槽位的模板下发了 `set_section_visibility(products,false)`
2. **再定修在哪一层**：生成端（①）还是注入端（②）
3. **静态区协议照建**，但它解决的是**另一件事**（"模板自带、系统不管"的区块），不是 A1 本身

> 原文档把这两件事混成一件，照它实施会修在错误的地方。

### 4.6 图片：**三级来源**（原为两级，2026-09-10 评估后升级）

```
① 客户提供原图  → <img src="assets/xxx.jpg">        真图，还原度最高
② 从截图提取    → <img src="assets/extracted-1.png">  ← 🆕 实测可行
③ 都没有        → <div class="ph ph--product"></div>  CSS 占位图形
```

#### 4.6.1 🆕 从截图提取图片（实测评估通过）

**这解决了本设计一直以来的最大缺陷**——“抠不出截图里的照片”。

**实测方案（已验证可行）**：

| 步 | 做法 |
|---|---|
| 1 | 让模型读截图，输出每张图片的**坐标框** `{label, x, y, w, h, confidence}` |
| 2 | **按缩放系数换算到原图坐标** |
| 3 | 用 `sharp` 裁剪出真实图片文件 |

**实测结果**：成功抠出截图里的沙丘照片（**65KB 有效图像**）。

> **🔴 必须记住的坑**：模型给的是**它自己缩放空间**的坐标，**不是原图像素**。
> 实测：原图 1440 宽，模型按 **800 宽**给的坐标 → **缩放系数 1.8**。
> 不换算直接裁 → **裁出空白**（实测 3.5KB vs 65KB，差 18 倍）。
> **这个坑不实测发现不了**，写进实现要求。

**依赖**：`sharp` **项目已装**（实测可用）。
**成本**：定位坐标仅 **1.5 秒 / 57 tokens**，可忽略。

**⚠️ 局限（如实）**：**只在单张图上验证过**。
多图、重叠遮挡、半透明背景、模型定位不准等情况**未验证** → 实施时必须做**置信度过滤 + 失败回退到占位**。

#### 4.6.2 占位图形库（仍然要建）

**设计系统的占位图形库**：产品类（风机/泵/阀/轴承）、背景类（城市/厂房/抽象）、图标类。
**全部纯 CSS 或内联 SVG**，不依赖外部图片——顺带满足「国内可直连」的既有要求。

**为什么有了抠图还要占位**：① 抠图会失败 ② 客户可能没给原图 ③ 有些素材（图标、装饰）本来就不该抠。

用户后续可在工作台替换：`onAssetSelect` 与 `/api/product-images` 已有。

### 4.7 门禁（决策 4）

复用并扩展 `lib/template-quality-gate.ts`。生成后**自动判**，不过关**带反馈重试**。

**新增检查项**（在现有「hero.title + 集合槽」下限之外）：

| 检查 | 理由 | 级别 |
|---|---|---|
| 静态区**不得嵌套**静态区 / scope | 见 §4.5.1 的 R3/R4 | blocker |
| 槽位**成对完整** | `features.items.N.title` 有、`.body` 没有 → 注入后一半是空的 | blocker |
| 无演示残留 | 已有（lorem / 作者名 / 英文看板） | blocker |
| CSS 可加载 | 引用的样式文件必须在产出里 | blocker |
| **CSS 质量下限**（新增） | 见下 | 见下 |
| 无外链关键资源 | 已有（境外依赖会让国内打不开） | warning |

#### 4.7.1 CSS 质量下限（原文档缺失）

原文档只查「CSS 文件在不在」。**模型写 5000 行垃圾 CSS、或选择器写错导致页面错位，照样能过门禁**——
而这恰恰是 §4.4 承诺"稳"却没人在守的地方。

| 检查 | 判据 |
|---|---|
| **体量上限** | 单模板 CSS ≤ 40KB（超过说明在做自由设计，没在用设计系统） |
| **必须引用设计系统** | 至少引用设计系统的变量/基础类，否则视为"重造轮子" |
| **关键类名存在** | 产出的 HTML 里用到的自定义类，CSS 中必须有定义（防"类名拼错→版式全塌"） |
| **响应式断点** | 至少一个 `@media`——工厂站大量用手机看 |

> **体量上限是刻意的**：它同时是"用没用设计系统"的**可测量代理**。
> 用了设计系统，CSS 会很小；没用的会膨胀到几十 KB。**用数字守约束，比写一句"请复用设计系统"可靠。**

**重试策略**（决策 8）：不过关 → 把 `blockers` 作为反馈喂回模型重生成，**上限 3 次**；
仍不过则**降级入库**——入库但标 `isolated`（不进 AI 推荐），**并告知操作人具体哪里没过**。

### 4.9 模板归属：**不沉淀全局模板库**（决策 9）

**用户决策**：截图生成的模板**不进全局模板库**——"没价值、费功夫，沉淀了还费功夫"。

**落地形态**：存本站本地，**不调 `POST /api/templates/runtime`**（那是全局注册表，所有人可见）。

> **这与阶段 A 的设计相反，要写清楚避免实现时走错**：
> 阶段 A 建的运行时注册表是为「**我们自己做的行业模板**」准备的（如 `vendor/industry-templates/fengji/`），
> 那些是**公共资产**；而客户上传截图生成的模板是**一等一的一次性产物**，混进全局库会污染它。

**代价（如实记录）**：同一个客户做第二个站，**不能复用**上一次生成的模板。若将来发现返工多，再考虑"把好的提成公共模板"的升级路径（这也是决策 9 留的口子）。

### 4.10 中途离开：**当成暂停，不是放弃**（决策 10/11/12）

**这是原设计完全没覆盖的场景**，由用户提出。见 §2.5 的缺口分析。

#### 4.10.1 三个缺口

| # | 缺口 | 现状 |
|---|---|---|
| G1 | **截图没地方存** | 只有 `product-images/`（商品图），**没有通用图片上传** |
| G2 | 🔴 **生成完了，用户一关页面就全丢** | `generate/route.ts:511` 检测到客户端断开就 `return`——**内容已生成、token 已花，却直接丢弃** |
| G3 | **找不到未完成的任务** | 首页只显示"站点名 + 模板ID"，看不出哪个是半成品；进去是 forge 工作台，**回不到上传界面** |

> **G2 的注释写了这是"有意为之"**——"保留『取消即中止写入』的保证"。
> 但那个保证是为**工作台里"我不要这次修改"**设计的；而**截图转模板场景下，"关页面"更可能是"我等不及了"**。
> **两件事被混成了一件。**

#### 4.10.2 设计（**刻意最小化，不照搬分布式那套**）

> **复审修正**：初版设计参考了 BullMQ（Redis 作业队列）的 `ownerToken` / 心跳 / `stallCount` / 内容寻址 sha256。
> **核实后判定为多余**——BullMQ 那套是为**多 worker 互相踩**设计的，而我们是**本地单进程**：
> 进程重启即意味着没有任何任务还在跑，磁盘上的 `generating` **必然是断的**，直接打回即可。
> **保留的只有状态机本身。**

**① 状态存在 `SiteRecord` 上，不新建存储**

复用既有模式（`sourceMaterial` 就是这么加的，`readRecord`/`writeRecord`/`withSiteLock` 全现成）：

```ts
export type SiteRecord = {
  siteId: string;
  draft: SiteDraft;
  // …
  sourceMaterial?: string;      // ← 已有（方向 2）
  templateJob?: {               // ← 新增，同一模式
    status: "uploaded" | "generating" | "done" | "failed";
    assets: string[];           //   指向 /api/uploads/{file}
    error?: string;
    step: "upload" | "generating" | "review";
    createdAt: string;
    updatedAt: string;
  };
};
```

PG 模式：加一列，与 `source_material` 同样的 `ALTER TABLE … ADD COLUMN IF NOT EXISTS`。

**② 图片：扩展现有上传接口，走中性前缀**

```
新：/api/uploads/{file}            ← 主用（截图 + 将来其他素材）
旧：/api/product-images/{file}     ← 保留，内部转发到同一实现，标 deprecated
```

**为什么保留旧路由**：磁盘上已有 29 张商品图，草稿与**已发布快照**里有 3 个文件引用了旧 URL。
已发布快照**本该不可变**——改它等于篡改历史记录。旧路由转发只需十几行，**不停机、零迁移**。

**③ 恢复：进程启动时打回**

```
启动 → 扫 status="generating" 的站点 → 一律打回 "uploaded"
```

**前提：本地单进程部署。** 若将来多实例，这条失效，届时才需要 BullMQ 那套锁与心跳。

**④ 清理（决策 11/12）**

```
status != "done" 且 updatedAt 超过 48 小时  →  删任务状态 + 删图片
status == "done"                          →  保留（成品，且要能重做）
```

**⑤ 首页入口（G3）**

```
鼎力风机设备                    ⏳ 模板制作未完成  [继续]
精工制造                        已完成
```

点「继续」→ 回到上传界面，**截图还在**，可补图、也可直接点生成。

#### 4.10.3 🔴 顺带发现的安全漏洞（**必须一起修**）

核实 B 方案时发现，**现在就存在**：

| 项 | 现状 |
|---|---|
| 上传白名单 | **接受 `image/svg+xml`**（`lib/product-image-store.ts:22`） |
| 读取接口 | 原样回 `Content-Type: image/svg+xml`，**无 CSP、无 `X-Content-Type-Options`、无 `Content-Disposition`** |

**SVG 可内嵌 `<script>`。同源提供 = 存储型 XSS。** 用户上传恶意 SVG → 他人打开 `/api/product-images/x.svg` → **脚本在我们的域名下执行**。

**而本设计会让上传接口接受更多素材（截图），攻击面只会更大。**

**修法（成本极低）**：读取接口加 `Content-Disposition: attachment` 或 `Content-Security-Policy: default-src 'none'`。
**用户已确认一起修。**

### 4.11 还要抄的一条：按钮状态

IndieHackers 的实测帖点名的**第一号 AI 产品 bug**：

> 用户点「生成」→ 按钮不变 → 等 2 秒 → **再点一次** → **请求发了两遍**。

**抄它的做法**：点击后立刻 `disabled` + 文案换「生成中…」+ spinner。
**服务端配合**：同一站点已有 `generating` 状态时，**拒绝第二次请求**。

## 五、分阶段交付

> **复审修正**：原 §五 写 B2 有"人工审一道"，但 §4.3 的流程图里**没有这一步**，两处矛盾。
> 结合**决策 5（客户自助）与决策 8（降级入库）**，正确形态如下——**人工审不是流程的一环**，

**B1.5 是新增的**：原设计把"三样约束"当成已有，实际全无。**跳过 B1.5 直接做 B2，等于让模型继续自由发挥**，
"快"与"稳"都不会发生。

## 六、验收口径

**B2 算通过的标准**（每一条都要有真实输出为证）：

1. 上传风机截图 → 产出一个模板，**全程无人工干预**
2. 产出的模板**过门禁**（无 blocker）
3. 在工作台**能看到与截图对应的版式**（分类格/产品卡/配色）——标准是**"大致像"**（决策 6），不苛求像素级
4. **产品区不被隐藏**（A1 已修）
5. AI 能填充内容，质量分可发布
6. `coverage-scan` 22/22 不回退
7. **耗时**：从上传到可预览 **≤3 分钟**（决策 5 客户自助；原文档写 ≤10 分钟，是内部代建的标准，已按自助调严）
8. **输入把关生效**：传一张非网页截图，**在生成前被拦下**并给出人话说明
9. **失败降级可用**：故意让门禁不过，确认模板仍入库、标 `isolated`、且操作人收到具体原因

> **第 7 条较原文档收紧**（10 分钟 → 3 分钟）：决策 5 定为客户自助后，等待容忍度完全不同。

## 七、待定 / 风险

1. **模型直出的稳定性**——即便有约束，不同次产出仍会有差异。**第一个版本不追求"完全一致"，追求"都合格"**。
2. **分类/资质的数据化**——本次决策是「静态区」。若将来客户要自己改分类，需要扩数据模型（`categories`/`certificates` 节），那是另一件工程。
3. ~~原图依赖~~ **已大幅缓解（2026-09-10）**：新增「从截图提取图片」（§4.6.1，实测可行），加上占位图形兜底，形成**三级来源**。**残余风险**：抠图只在单张图验证过，多图/遮挡/透明背景未验证，实施时需容错。
4. **多页**——本次不做。多页做成**模板可选属性**（有 `pages` 声明才是多页），不与本设计耦合。
5. **成本上限未测算**（新增）——自助上传意味着**调用量不可控**。目前只知读图 847 tokens/张，
   **一次完整生成（含重试）的成本还没测**。上线前必须测，否则可能被刷。
6. **生成失败率的真实值未知**（新增）——B1 手工那轮实测 3 次失败 1 次（A2），
   但那是"模型改内容"，**与"模型生成模板"是两件事**，后者的失败率还没数据。
7. **自助场景下的滥用防护**（新增）——无频次限制、无额度控制。决策 5 一旦上线，
   **任何人都能烧 token**。这是产品设计问题，本文档不覆盖，但**必须在上线前解决**。
