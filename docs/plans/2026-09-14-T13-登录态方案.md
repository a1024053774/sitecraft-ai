## 〇、事实基线（取证，非推理）

**后端怎么判**（`lib/request-context.ts:77-99`）：

```ts
// ① 模式：显式设了就用；否则非 development 一律 strict
function configuredMode() {
  const explicit = process.env.SITECRAFT_ACCESS_MODE?.trim();
  if (explicit === "strict" || explicit === "relaxed") return explicit;
  return process.env.NODE_ENV === "development" ? "relaxed" : "strict";
}

// ② strict 下三个头缺一即 401
if (mode === "strict" && (!workspaceId || !actorId || !roleValue)) {
  return error("access_context_required", 401, "需要内部访问上下文才能访问该资源。");
}

// ③ 缺值时回落
const resolvedWorkspace = workspaceId || fallbackWorkspace;  // DEFAULT_WORKSPACE_ID ?? "demo"
const resolvedActor = actorId || "internal-dev";
const resolvedRole = roleValue || "editor";                   // ← 可写
```

三个头：`x-sitecraft-workspace-id` / `x-sitecraft-actor-id` / `x-sitecraft-role`。

**前端怎么发**：**一个都不发**。全仓 43 处 `fetch("/api/...")` 分在 13 个文件里：

```
app/{content,export/[siteId],generate,leads,page,published/[siteKey]/client,templates,workspace}
components/{app-sidebar,client-preview-frame,create-template-dialog,generation-health-panel,start-site-button}
```

**两条路由是唯一例外**——它们**转发**这三个头（`from-url` / `from-screenshot`）：

```ts
...(request.headers.get("x-sitecraft-workspace-id") ? { "x-sitecraft-workspace-id": ... } : {}),
```

**这就是双断链**：前端不会发 → 转发逻辑拿到空 → 后端 strict 判 401。

**e2e 为什么一直是绿的**：`e2e/scripts/serve.mjs` 显式设了 `relaxed`。
**生产（非 development）默认 strict** → **22 个「端点×方法」必然 401，整站不可用**。

## A · 维持现状 + 网关注头

### 改动面

- **本仓库代码：0 行。**
- 部署侧：在反向代理（nginx / ALB / Cloudflare 等）统一注入三个头，
  并**显式设** `SITECRAFT_ACCESS_MODE=strict`；
- 需要一份**部署配置文档 + 一个冒烟脚本**（对三个核心入口断言"缺头 401 / 带头 2xx"）。

### 风险

- ⚠️ **单租户假设被固化**：网关只能注入**一组固定值**（如 `demo / gateway / editor`）
  ——**所有请求都是同一个工作区、同一个可写身份**。
  本仓库的"多工作区"能力从此**只在代码里、不在部署里**。
  若将来要做多租户，这次注入的常量就是**必须拆掉的债**；
- ⚠️ **把安全边界放在应用之外**：任何绕过网关的路径（内网直连、端口暴露、
  `kubectl port-forward`）都能拿到 `demo` 工作区的**可写**身份。
  应用的 `strict` 判定**只防了漏设环境变量，没防绕过网关**；
- ✅ 但**当前形态下这不构成新增风险**：本仓库现在**没有登录体系**，
  本来就无法区分"用户 A / 用户 B"。A 不是"把安全的做不安全"，是"承认现状"。

### 回退成本

- **≈ 0**：回退 = 撤掉网关的注入规则（改代理配置），仓库代码零改动；
- 但要**注意**：一旦按 A 上线，任何"绕网关直连"的既有调用方会继续静默可用，
  回退后**不会**自动变安全——需要在回退清单里单独检查。

## B · 前端登录态 / 凭据签发

### 改动面

**分两段，工作量差一个量级**：

- **B1（小，~1 天）**：加一个**统一的 `apiFetch` 包装**，自动带三个头；
  把 **43 处 `fetch("/api/...")` 全部换掉**（13 个文件）；
  头值来自一个 `NEXT_PUBLIC_*` 环境变量或运行时配置。
  ——**本质仍是常量注入，只是从网关挪进了浏览器**。
- **B2（大，多天）**：真正的登录态——签发凭据（cookie / JWT）、
  服务端校验签发方、`workspaceId` 从**凭据**而非请求头读。
  这需要**引入 auth 依赖**、改 `resolveAccessContext` 的判定来源、
  加登录页、加会话存储——**是一次架构变更，不是补一个头**。

### 风险

- ⚠️ **B1 把秘密放进了浏览器**：`NEXT_PUBLIC_*` 会进客户端包，**任何人可读**。
  这等于「把网关的注入逻辑公开化」——**安全性比 A 更弱**（A 至少还挡在代理后）；
- ⚠️ **B2 会触碰红线**：改 `resolveAccessContext` 的判定来源 = 改鉴权判定的
  **权威定义**（`lib/request-context.ts` 是 `lib/` 契约层）；
  B2 还必须决定"未登录用户能看什么"——这是**产品决策**，不只是技术改动；
- ⚠️ 43 处替换本身**没有门禁保护**：漏一处就是一个静默 401，
  而现有 e2e 全跑 relaxed，**漏了也不会红**（需要新增"全量 fetch 必须走
  `apiFetch`"的结构检查，否则又是一次假绿）；
- ✅ B2 做完才是**真正可用的多租户**：`workspaceId` 来自身份而非请求头，
  绕过网关也拿不到别人的数据。

### 回退成本

- **B1：中**——43 处替换要整体回退（但都在 13 个文件内，`git revert` 一次即可）；
- **B2：高**——涉及依赖、判定来源、产品决策三处，回退 = 撤销一次架构变更。

## 倾向（供拍板参考，非结论）

**当前形态**（无登录、单部署、无多租户诉求）→ **A** 是正确的工程判断：
它承认现状、零代码改动、回退成本近零，且**比 B1 更安全**（不进浏览器）。

**B 的价值在将来**：等真的要做多租户 / 多人协作时再做 B2。
**B1 不建议单独做**——它花 1 天得到的是"比 A 更弱的安全性"。

⚠️ **无论选哪个，都必须补一条**：部署文档里写明
**「`SITECRAFT_ACCESS_MODE` 不设时，非 development 默认 strict」**，
以及**三个头的权威来源**。当前这条规则只活在代码注释里。
