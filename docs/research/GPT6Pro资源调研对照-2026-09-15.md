# GPT-6 Pro 调研对照与采用边界（2026-09-15）

> 输入：`resources/调研结果.md`、`resources/SKILL.md`、`resources/resources.json`。
> 证据边界：该资料包只做了公开官方来源检索，没有读取本项目代码、安装外部 Skill、运行模板或做效果基准；因此本文记录为研究输入，不是生产准入。

## 可采用的核心增量

### 1. 方案从三件套升级为受控交付链

原始想法“Skill + 模板 + 提示词”仍然有价值，但不足以保证成品质量。更完整的链路是：

```text
企业事实与目标
  → 行业简报 / visualBrief
  → 授权素材清单
  → 模板与区块能力筛选
  → DESIGN.md / 设计 token
  → page-plan.json
  → 受控 operations / renderer
  → 浏览器截图与功能验收
  → 独立审查与有限轮次修复
  → 预览确认 / 发布
```

新增的两个本地契约候选：

- `DESIGN.md`：色彩语义、字体、字阶、间距、内容宽度、图片裁切、圆角、动效和移动布局；
- `page-plan.json`：页面目的、受控 section ID、文案字段、素材 ID、主要行动路径。

它们不能替代现有 `visualBrief`、slot map 和 operations，而是需要合并成同一套版本化设计/页面计划契约，避免形成平行系统。

### 2. 先决定交付模型

| 模式 | 交付 | 许可影响 |
| --- | --- | --- |
| 内部 AI 代建 | 团队接需求，最终交付某一家企业网站 | 某些商业模板可能允许普通客户交付，但需核对团队席位、客户交付、AI 使用和修改范围 |
| 自助建站平台 | 客户自己输入需求、生成、复制或导出网站 | 优先使用可核验、允许平台嵌入和再分发的开源/原创资源；商业模板不能按普通客户网站许可推断可用 |

当前项目目标更接近第二种，但这是产品负责人需要确认的关键决策。没有确认前，商业模板和商业区块不进入平台池。

### 3. Skill 按职责串联，不叠加多个审美主控

资料包建议的职责划分有价值：

- UI UX Pro Max：需求/行业/设计系统候选检索；
- 只选一个审美主 Skill：Impeccable 或 frontend-design，不能让多个审美 Skill 同时争夺主控；
- Marketing Skills：按需组织真实企业文案和转化结构；
- web-design-guidelines：生成后规范审查；
- agent-browser：真实浏览器交互、截图和状态验收；
- 项目自己的 `smb-site-orchestrator`：负责事实、素材授权、模板适用性、设计系统、页面计划和截图交付流程。

这与此前“Skill 不是 DeepSeek 运行时能力”的结论一致。运行时仍需要把结果转成 `visualBrief`、page plan 和白名单 operations。

### 4. 行业包应改变信息结构，不只是换颜色

优先行业候选：

- 本地服务：清洁、维修、园林、家政；
- 制造/设备/零部件/外贸 B2B；
- 咨询、会计、法律等专业服务；
- 餐饮、民宿、美容、健身等真实场景业务；
- 软件/SaaS/数字服务。

每个行业包应规定：核心访客、主要行动、必须出现的信息、可信素材类型、允许缺失的字段和适合的页面结构。行业包不能覆盖真实品牌事实，也不能代替客户资料。

### 5. 素材要独立治理

资料包建议把素材记录为：

```text
素材 ID → 原始来源 → 使用许可 → 客户确认状态
       → 适用页面 → 图片比例 → 主体裁切位置 → 是否属于企业事实
```

尤其要区分：

- 客户真实工厂/团队/项目/产品图；
- 经授权的图库场景图；
- 仅用于抽象氛围的生成图。

图库或生成图不能冒充客户员工、真实项目、真实产品或实际业绩。

### 6. 小规模对照实验比继续堆模板更重要

资料包建议做 3 个行业、每行业 2 个完整 brief，共 6 个案例；每个案例比较：

- A：当前默认流程；
- B：当前流程 + 一个审美主 Skill；
- C：B + 行业路由 + 合适模板/区块 + 设计系统；
- D：C + 真实截图审查 + 最多两轮局部修复。

共 24 个结果。需要记录：人工审查时间、修复轮数、成本、截图和用户选稿偏好。不能同时更换模型、模板、素材和提示词后把收益归给某一个 Skill。

## 与当前 SiteCraft 方案的合并结果

### 保留

- 现有 D/B 混合路线：先做 iframe 模板约束闭环，再用证据决定原生 React 轨；
- `visualBrief`、slot map、asset plan、structured operations 和 `commitOperations`；
- 三个已知事实包 + 一个未见事实包的独立评测思路；
- 机器否决项 + 截图 + 人工盲评，而不是模型美观自评；
- 先做 1–2 个行业和少量模板，不先扩 16 套；
- agent-browser 类真实浏览器验收作为后续能力候选；
- 设计主 Skill 只选一个，审查 Skill 与文案 Skill 分职责。

### 修正

- “top5 先做”仍是阶段门，不等于首个切片必须同时实现 5 套；首个验证建议先 `forge` + 一套相邻模板，再扩 top5。
- `DESIGN.md` 和 `page-plan.json` 不单独成为第二套契约；它们应被吸收进 `visualBrief`、模板 manifest 和页面/section plan。
- UI UX Pro Max、Impeccable、Marketing Skills 先作为候选对照，不直接全部 vendor 或加载；需要先锁版本、许可证、运行方式和效果基准。
- Tailark OSS、HyperUI、AstroWind、Astroplate 等只进入候选池；当前仓库已有模板和 iframe 适配成本，不能因为候选看起来更好就扩大模板池。
- CodeStitch、Lexington、Shadcnblocks、Tailwind Plus 等商业资源不进入自助平台默认池；如业务转为内部代建，再单独做授权评估。

### 冲突与未验证

- 资料包把 UI UX Pro Max、Impeccable 和 Marketing Skills 标为 P0 候选，但没有在本项目安装、运行或对照测试；本项目当前只核验过 frontend-design、web-design-guidelines 的来源信息。
- `resources.json` 对 Vercel web-design-guidelines 的完整许可证标为待核对，与此前报告的 MIT 结论存在证据层差异；生产准入前必须直接固定上游文件和 SHA。
- 资料包推荐 AstroWind/Astroplate，但当前主线已经有 16 套模板和 iframe bridge；是否新引入取决于技术栈、snapshot、slot 覆盖和许可证复核。
- 资料包建议 24 个结果的人工实验；当前项目尚无盲评基线、目标客户代表或固定截图环境，因此这是待确认的实验预算，不是当前门禁。

## 当前建议

在产品负责人确认交付模型和首批行业前，不安装或接入新增 Skill/商业模板。下一轮 grilling 先确认：

1. 内部代建还是自助建站平台；
2. 首批行业和网站类型；
3. 用户必须提供的事实和素材；
4. 设计主 Skill 是否只选一个，以及候选对照方式；
5. 是否接受 3 行业 × 2 brief × 4 组的首轮实验预算；
6. 商业资源全部排除，还是允许内部代建模式单独评估。
