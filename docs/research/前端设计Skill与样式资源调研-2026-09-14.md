# 前端设计 Skill 与 React/Next/Tailwind 样式资源调研

> 研究目的：为 SiteCraft AI 选择可审查的前端设计 Skill、React/Next/Tailwind 样式资源，并明确接入边界。
>
> 研究日期：2026-09-14
>
> 项目基线：当前仓库是 Next.js 16.3.1 + React 19.2.0，主应用使用自有 CSS 变量与组件样式；仓库没有把 Tailwind 作为主应用依赖，模板目录另有 Tailwind/框架实现。
>
> 本文是原始调研记录。**如何落地、先后顺序、与升级任务书的关系，以 [`docs/plan/项目总规划-2026-09-15.md`](../plan/项目总规划-2026-09-15.md) 为准**；两者冲突时规划文档优先。

## 结论

建议采用"两个 Skill + 一个基础组件层 + 少量视觉增强"的组合：

1. **frontend-design**：负责生成前的视觉方向、字体、色彩、版式和反模板化约束。
2. **web-design-guidelines**：负责生成后审查可访问性、响应式、交互、表单、性能和文案。
3. **shadcn/ui + Radix Primitives**：作为可复制、可改造、可版本化的基础组件层。
4. **21st.dev、Magic UI、Aceternity UI**：只作为经过许可审查的灵感或局部组件来源，不直接把整套社区内容接进生成器。

核心接入链路应保持为：

`frontend-design` → `visual brief` → 模板匹配与 asset plan → 生成操作 → 浏览器截图与 guidelines 审查 → 发布门禁

这与之前对 PR4 的判断一致：设计 Skill 不能绕过现有生成操作白名单；应先转成项目自己的、版本化的 `visual brief / asset plan` 契约。

## 面向当前仓库的落地顺序（原稿）

### 第一阶段：先建立设计契约

新增一个版本化的 `visual brief` 数据结构，至少包含：

- 行业、受众、语言和转化目标
- 风格方向与禁用风格
- 字体组合、色彩角色、间距密度、圆角和阴影
- 页面骨架：导航、hero、产品/内容区、信任区、CTA、页脚
- 动效级别与 `prefers-reduced-motion` 策略
- 图片角色：hero、product、wide、other，以及来源、许可证、比例和 hash

让模板匹配、素材规划和生成操作都读取同一份契约；不要让 Skill 直接写任意 CSS 或绕过 `commitOperations`。

### 第二阶段：做一个最小组件竖切

只选 shadcn/ui/Radix 的 Button、Form、Dialog、Tabs、Table、Sidebar，接到一个真实模板预览。验收：

- 组件可在桌面、平板、手机画布工作
- 键盘和焦点状态可操作
- 表单错误和空状态可见
- 截图结果与 visual brief 的字体、色彩和布局一致
- 不引入无法追踪来源的复制代码

### 第三阶段：再加入视觉增强

从 21st.dev、Magic UI 或 Aceternity UI 各挑少量候选，逐项记录许可证和来源。每个候选都要经过：

1. 代码与依赖审查；
2. 许可证与归属记录；
3. 运行时性能和可访问性检查；
4. 浏览器截图回归；
5. 明确是否允许进入可复用素材/组件库。

## 风险与未决项

- **21st.dev 不是可任意镜像的数据源**：条款对抓取、训练、媒体和再发布有明确限制；应采用人工选择、保留回链和逐项许可记录。
- **视觉 Skill 不等于行为正确**：必须把 guidelines 审查和真实浏览器验证设为独立门禁。
- **当前主应用不是 Tailwind 主栈**：直接引入大量 Tailwind 组件会造成样式体系分裂；优先把 token 和交互契约抽象出来，再决定是否局部引入。
- **付费资源不能默认进入用户建站产品**：Tailwind Plus 等商业 UI kit 可能禁止再分发或让终端用户基于其构建产品；需要法务/许可确认后再用。
- **agent CLI 检索状态**：本次按要求调用了本机 `agent --print --mode ask --workspace ...` 两次，但均长时间无输出后中止；网页事实改由官方页面核验，CLI 检索结果为未取得。

## Grok Bot 云电脑复核（2026-09-14 16:47）

Grok Bot 使用其云电脑联网核验了官网、ToS、GitHub、raw 文件和 npm 元数据。它没有修改项目代码，报告补充如下：

### 复核后的优先级

- **P0：shadcn/ui + Radix**：作为默认设计系统和组件底座，MIT，可复制改造；建议建立 SiteCraft 私有 registry。
- **P0：Anthropic frontend-design**：Grok 找到的 Skill 目录许可证为 Apache 2.0，适合改编为 `sitecraft-frontend-design`；文档类 Skill 不能按开源 Skill 处理。
- **P0：Vercel web-design-guidelines + react-best-practices**：上游 `web-interface-guidelines` 有 MIT 许可证；`agent-skills` 包装仓库的根许可证证据不完整，建议 vendor 并 pin SHA，不要每次直接拉 `main`。
- **P1：21st.dev 官方 MCP/CLI**：适合按需发现和安装组件；不要建立 Marketplace 镜像或抓取目录。
- **P1：Magic UI 免费核心**：MIT，可作为少量营销动效；Magic Pro 源码不进入生成管线。
- **P1 保守：Aceternity UI 免费组件**：网站条款、npm 与组件许可表述需要逐项核对，暂不批量注入。
- **避免：Tailwind Plus 及各类 Pro 源码**：专有许可可能禁止网站生成器让终端用户继续构建 End Product。

### 21st.dev 重点核验

Grok 复核到的平台代码/CLI 与 Marketplace 内容不是同一许可层。Marketplace ToS（2026-07-20）明确限制自动抓取、训练模型、未授权再分发、复制展示媒体和结构化元数据；即使某个组件代码本身允许复制，也不等于获得 demo、缩略图和平台编排内容的权利。SiteCraft 应采用官方 MCP/CLI 的按需拉取方式，保留原始组件链接和作者归属，禁止自建镜像目录。

### 推荐接入顺序

1. **合规基线**：只允许 MIT/Apache 明确可再分发的资产进入默认产物，并生成第三方 notice。
2. **Skill 与质量闭环**：改编 frontend-design；vendor 并固定 Vercel 规则；接入 react-best-practices。
3. **默认生成栈**：shadcn/ui + Radix + SiteCraft 私有 registry；Magic UI 只放 MIT 免费白名单。
4. **社区发现**：通过 21st 官方 MCP/CLI 执行 search → get component → 写入用户项目，带回链，不镜像。
5. **谨慎扩展**：Aceternity 逐项法务核验；Pro 组件只用于 SiteCraft 自有官网，不进入客户生成物。

### 仍需人工确认

- 21st 组件逐页 license 字段及是否存在 Partner 再分发协议；
- Aceternity 免费组件是否有独立、明确的 MIT 文件；
- Vercel `agent-skills` 根 LICENSE 是否补齐；
- Anthropic 插件页与 GitHub Skill 是否同版本；
- SiteCraft 当前运行时是否已经支持 Agent Skills / `npx skills`。

这次 Grok 调研与本页原结论一致：默认栈用 shadcn + Radix，设计意图用改编后的 frontend-design，质量审查用钉扎版本的 Vercel guidelines；21st 作为官方渠道的发现层，绝不镜像。
