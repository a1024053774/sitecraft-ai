# 6Pro 调研结果

你的方向值得继续，但我建议把 **“Skill + 模板 + 提示词”升级为“行业简报 + 授权明确的素材池 + 设计系统 + 受控生成 + 截图验收”**。

核心不是让 AI 多记几条“不要紫色渐变、不要千篇一律卡片”的规则，而是让它知道：**这家企业卖什么、访客为什么来、哪些内容最值得展示、现有素材能支撑哪种设计，以及生成后哪里没有做好。**

我按官方仓库、产品文档和许可条款做了筛选，核查日期为 **2026 年 9 月 15 日**。下面是选型建议，不是安装后的实测排名；也还不能据此判断你项目里的模板究竟差在模板本身、选择逻辑还是生成流程。

**第一轮最值得试的组合：UI UX Pro Max 做行业与风格选型，Impeccable 做设计与改造，Marketing Skills 做有事实依据的文案，现有工程配合合适的模板底座，最后用真实浏览器和 Vercel 的规范做验收。**

## 一、先解决一个会影响整个方案的问题：代建服务与自助建站平台，要用不同的素材策略

你描述的业务可能走向两种模式：

| 模式                     | 实际交付                                               | 我建议的素材策略                                             |
| ------------------------ | ------------------------------------------------------ | ------------------------------------------------------------ |
| **内部用 AI 帮客户代建** | 你接需求，用 AI 辅助制作，最终交付某一家企业的网站     | 可以考虑适当购买商业模板，但需核对客户交付、团队席位和 AI 使用范围 |
| **把 AI 建站做成产品**   | 客户在平台输入需求，选择风格，自动生成、复制或导出网站 | 优先审核开源素材及原创模板；商业模板需要核对生成器、平台嵌入和再分发授权 |

这不是形式上的区别。**Shadcnblocks 的许可明确限制网站生成器，以及将组件纳入供用户生成网站或应用的工具；允许做普通客户网站，不等于允许把它装进你的 AI 建站平台。** [Shadcnblocks.com](https://www.shadcnblocks.com/license)

因此，我不建议现在直接购买一个“大而全模板包”，然后把全部内容塞进项目。先明确交付模型，避免后面重新替换素材。

### 我会怎样组合

不建议这样的做法：

> 同时加载三个“审美专家 Skill” → 给一句“高级、现代、去 AI 味” → 直接生成整站。

我建议分阶段调用：

```
企业资料与需求
    ↓
UI UX Pro Max：检索候选方向
    ↓
确定设计系统，只选一个审美主 Skill
    ↓
Marketing Skills：组织真实文案
    ↓
Impeccable 或 frontend-design：实施设计
    ↓
Vercel 规范 + 真实浏览器：审查
    ↓
局部修复，而不是整站重写
```

Agent Skills 的规范本身也采用按需加载的方式：先提供技能名称和描述，需要时再加载完整指令和相关资源。你没有必要把所有 Skill 全文放进每次请求。[Agent Skills](https://agentskills.io/client-implementation/adding-skills-support)

**对你这个项目，更值得自建的 Skill 是“如何使用我们自己的模板和组件”，而不是再写一份泛泛的“如何拥有高级审美”。**

这一点已有可参考的组织方式：AstroWind 的仓库包含配套技能和组件用法目录，让 Agent 知道组件有哪些、参数怎样传、在哪里有示例。[GitHub](https://github.com/arthelokyo/astrowind/blob/main/.agents/skills/use-widgets.md)

## 三、模板和前端素材：建议拆成“整站底座、页面区块、视觉点缀”三层

整站模板解决页面体系和工程组织；区块解决布局选择；动效组件只是点缀。把这三者混为一谈，很容易得到“每一块单独看都不错，拼起来不像同一个品牌”的网站。

### 1. 优先审核的开源来源

以下是**待审候选池**，不是已经批准的生产白名单。

## 四、图片、字体和参考站，也要进入约束体系

在你的方案里，我会把素材选择设为独立步骤，而不是让模型生成页面时临时搜索一张“business”图片。

| 类型                   | 推荐来源                       | 使用方法                                                     |
| ---------------------- | ------------------------------ | ------------------------------------------------------------ |
| **摄影与场景图**       | Unsplash、Pexels               | 客户原图不足时作为补充。不要把图库人物、建筑或产品冒充客户员工、实际项目、门店或产品。两个平台均有各自许可和限制。[Unsplash](https://unsplash.com/license) |
| **图标**               | Lucide                         | 一个网站尽量统一一套图标，减少线宽、尺寸和风格不一致；遵守其许可声明。[Lucide](https://lucide.dev/license) |
| **中文与中英混排字体** | Noto Sans CJK / Noto Serif CJK | 将中文字体作为设计系统的一部分，单独测试字重、换行和手机端效果；Noto 采用 OFL。[GitHub](https://github.com/notofonts/noto-cjk) |
| **设计方向参考**       | Land-book                      | 用来查不同视觉方向和排版方式，不把“看得见”当成代码、图片或模板的使用授权。[Land Book](https://land-book.com/) |
| **单页与模板发现**     | One Page Love                  | 用作发现入口，再回到原作者处核验技术栈和许可，不将整个目录视为统一授权素材库。[One Page Love](https://onepagelove.com/templates) |

如果通过 Unsplash API 自动选图，还要单独遵守 API 的署名、图片链接及下载统计等要求，不能只看普通图片许可。[Unsplash](https://unsplash.com/documentation)

我建议为每张可用素材记录：

```
素材 ID → 原始来源 → 使用许可 → 客户确认状态
       → 适用页面 → 图片比例 → 主体裁切位置 → 是否属于企业事实
```

最后一个字段很重要：**工厂实拍、真实员工照、实际项目图，与仅用于烘托气氛的图片，不能在生成流程里当成同一种素材。**

## 五、行业包应该怎样做：不是换颜色，而是换信息结构

下面是我建议建设的行业包，不是承诺某个现成模板已经实现了这些功能。预约、询盘、CMS 等仍需要接入和测试。

| 行业场景                         | 建议视觉方向             | 页面中应该优先出现什么                           | 主要行动           | 可考察的底座或参考                      |
| -------------------------------- | ------------------------ | ------------------------------------------------ | ------------------ | --------------------------------------- |
| **清洁、维修、园林、家政**       | 真实、清楚、有地域感     | 服务项目、覆盖地区、实际作业、工作流程、联系方式 | 电话或询价         | HyperUI、AstroWind；CodeStitch 行业参考 |
| **制造、设备、零部件、外贸 B2B** | 克制工业感、参数清楚     | 产品分类、规格、工艺、实际能力、核验过的资质     | 询盘或索取规格     | AstroWind、Astroplate、原创规格区块     |
| **咨询、会计、法律服务**         | 编辑式、稳重、阅读舒适   | 服务对象、具体交付、真实团队、工作方法           | 预约沟通           | Astroplate、HyperUI；Lexington 行业参考 |
| **餐饮、咖啡、民宿**             | 真实摄影、品牌色、轻导航 | 菜单或房型、空间、营业时间、位置                 | 看菜单、预订或导航 | AstroWind、HyperUI；CodeStitch 参考     |
| **美容、健身、工作室**           | 温和、人物与空间优先     | 服务内容、人员资料、环境、价格或咨询方式         | 预约体验           | HyperUI、行业定制区块                   |
| **建筑、室内设计、摄影**         | 作品主导、少装饰         | 项目图片、项目详情、真实参与范围、工作方法       | 提交项目需求       | Lexington 参考、原创作品集区块          |
| **培训、企业教育**               | 内容清楚、适度亲和       | 课程对象、大纲、师资、时间地点                   | 课程咨询           | Astroplate、HyperUI                     |
| **软件、SaaS、数字服务**         | 产品展示优先、少量动效   | 真实产品截图、工作流、适用场景、已实现功能       | 预约演示或试用     | Tailark OSS、shadcn/ui、少量 Magic UI   |

这里有个很有用的选型原则：

**先看企业有多少真实素材，再选模板；不要先选大图模板，再让 AI 找图片把空位填满。**

例如，一个没有项目照片的工业企业，可能更适合“产品图 + 参数表 + 流程说明”的结构，而不是强行套用摄影驱动的品牌展示模板。没有案例授权的咨询公司，也可以展示方法和交付内容，不必编造客户评价。

### 对“去 AI 味”，我建议这样定义

不要把它定义成“禁止紫色、禁止居中标题、禁止圆角卡片”。这些元素本身不是问题。

可以把评审问题改为：

> 这套内容和布局，是否只有换成另一个公司名称也完全成立？
> 这个行业最重要的信息，是否被装饰和通用营销话术挤到了后面？
> 页面是否真正体现了客户的产品、空间、团队和工作方式？

一个制造企业官网如果只是“赋能未来—三项优势—四个数字—客户评价—立即开始”，即使改成黑白极简，仍然可能只是换了一种模板感。

## 六、项目内部建议采用什么方案

我建议采用 **“受控模板生成为主，局部代码生成补充，真实截图审查收尾”** 的方式。

### 1. 模板先建立元数据，而不是只存一张预览图

每个模板或区块至少应记录：

| 维度     | 应记录的内容                                 |
| -------- | -------------------------------------------- |
| 工程兼容 | 技术栈、版本、依赖、源码修订号               |
| 业务适配 | 行业、页面类型、主要行动、适用内容密度       |
| 视觉适配 | 视觉家族、字体、色彩、布局密度、动效级别     |
| 素材要求 | 是否需要人物照、大图、产品图、案例图、参数表 |
| 内容约束 | 必填内容、允许缺失的字段、长度与溢出处理     |
| 授权状态 | 代码许可、图片许可、是否批准平台嵌入         |
| 验收记录 | 手机与桌面截图、已测状态、已知问题           |

**选择顺序应该是：先排除不能用的，再在能用的里面选最好看的。**

例如，先按许可、技术栈、语言、素材和业务需求过滤，再比较行业匹配、品牌匹配和改造成本，而不是先做一个“视觉相似度最高”的检索。

### 2. 先生成页面计划，再生成页面

建议的内部链路：

```
客户 brief + 核验过的事实 + 素材清单
    ↓
行业包与模板筛选
    ↓
DESIGN.md + 设计 token
    ↓
page-plan.json
    ↓
受控组件渲染 / 必要的局部代码生成
    ↓
浏览器截图 + 功能检查
    ↓
独立审查 + 有限轮次修复
    ↓
预览确认与发布
```

`page-plan.json` 负责表达“这页要什么区块、用哪些文案和图片、用户最后去哪里”，而不是让模型每次任意重写所有组件。

React 方向可参考 shadcn Registry 的组织方式，建立你自己的、经过审核的区块入口；这是一种可借鉴的分发机制，不意味着要照搬所有外部组件。[shadcn/ui](https://ui.shadcn.com/docs/registry)

### 3. 子代理适合分工，但不宜同时随意改页面

对于后续实际实现，我建议先用以下职责划分：

| 职责           | 主要输出                         | 不应做什么                         |
| -------------- | -------------------------------- | ---------------------------------- |
| 需求与资料核验 | 企业 brief、缺失项、事实与素材表 | 编造企业信息                       |
| 设计负责人     | 页面结构、设计系统、模板选择理由 | 不受限制地增加特效或依赖           |
| 实施者         | 页面代码与真实业务连接           | 擅自改变已确认的设计方向           |
| 独立审查者     | 基于截图和测试的具体问题         | 只输出“更高级一些”，或直接整站重写 |

起步时不必真的启动四个并行 Agent。**一个实施者，加一个上下文独立的审查者，就足以验证闭环是否有价值。** 选型、资料和设计可以分阶段完成，避免多个代理同时修改同一批文件。

### 4. 提示词应约束交付事实，而不只是审美形容词

值得写成硬规则的是：

> 所有数字、认证、客户 logo、评价和项目必须有来源；缺失则省略或标为待补。
> 全站使用同一套设计 token。
> 审查必须基于实际截图，并指出页面、断点、区域和最小修复方案。
> 修复手机端布局时不得无理由重写整站。
> 表单未在测试收件端验证之前，不得宣称询盘功能已接通。

相比“高级感、商业感、现代感”，这些约束更容易验证，也更容易沉淀为稳定交付能力。

还应提前明确：**客户上线后怎样修改营业时间、产品、价格和案例。** 我会把这些做成结构化内容字段或接入现有 CMS，而不是每次修改都重新生成整站代码。

## 七、最小验证方案：先做 24 个结果，判断什么真的有效

现在没有必要先搭一个庞大的模板市场。我建议先选 **3 个行业，每个行业 2 份完整简报，共 6 个案例**。

每个案例做四组：

| 组别  | 流程                                    | 要回答的问题                 |
| ----- | --------------------------------------- | ---------------------------- |
| **A** | 当前默认流程                            | 现在的真实基线是什么？       |
| **B** | 当前流程 + 一个审美主 Skill             | 单加 Skill 是否有效？        |
| **C** | B + 行业路由 + 合适模板/区块 + 设计系统 | 主要提升是否来自素材与结构？ |
| **D** | C + 真实截图审查 + 最多两轮修复         | 审查回路是否值得额外成本？   |

这样首轮共 **24 个结果**。各组使用相同模型、同一份客户事实和可用素材，记录额外的审核成本；不要同时更换模型、补拍照片和替换模板，然后把全部收益归给 Skill。

### 评审不要只看模型自己的分数

建议隐藏组别，随机展示给目标客户代表和设计评审。可先采用以下项目自定权重：

| 维度                         | 建议权重 |
| ---------------------------- | -------- |
| 品牌识别、视觉层级与整体质感 | 35       |
| 行业适配与信息结构           | 25       |
| 文案、图片和企业信息可信度   | 20       |
| 可读性、手机端与主要操作     | 20       |

同时记录每站成本、人工修改分钟数、修复轮次和客户选稿偏好。**这些权重是试点建议，不是行业标准；审美改善也不能直接当成转化率改善。**

技术验收另外设硬门槛：关键页面存在，导航可用，手机端无明显溢出，表单真的到达测试收件端，素材授权清楚，不存在虚构企业事实。

浏览器截图可先覆盖 **375、768、1440 像素宽度**以及菜单、表单错误等状态。Playwright 能帮助做截图回归，但截图一致只是防止退化，不意味着设计本身优秀。[Playwright](https://playwright.dev/docs/test-snapshots)

性能也应与审美分开：Lighthouse 用于实验室诊断；上线后再观察真实用户的 Core Web Vitals，而不是把一次跑分当成所有客户访问都良好。当前良好体验阈值包括 LCP 不超过 2.5 秒、INP 不超过 200 毫秒、CLS 不超过 0.1，并按第 75 百分位评估。[web.dev](https://web.dev/articles/vitals)

## 八、我建议你现在采用的路线

**不推翻现有项目，先增加三个环节：模板元数据与筛选、企业事实和设计系统、真实截图审查。**

首轮只接入少量来源：

- **设计主流程：** Impeccable，配合 UI UX Pro Max 做前置选型；Anthropic frontend-design 和 Taste Skill 留作对照。
- **素材底座：** 按现有技术栈，在 AstroWind / Astroplate 或 shadcn/ui + Tailark OSS + HyperUI 中选一条主线，不混装全部。
- **行业差异：** 先做本地服务、工业 B2B、专业服务三个行业包，优先补真实业务结构和素材要求，而不是增加几十套颜色主题。

随后用上面的对照实验判断问题到底在哪里：Skill 没被正确触发、模板选错、素材不足、文案空泛，还是生成后根本没有视觉检查。

我已把调研结果整理成资料包，包含 **30 项官方资源与规范入口、8 个行业包草案、一个原创建站编排 Skill、独立视觉审查提示词、模板元数据示例及实验计划**。其中没有第三方付费模板、字体文件，也没有已安装或实测的承诺；资源默认均未获生产准入。
